# Open points

Points the decisions do not settle yet, listed by the card that has to settle them. They come from tracing one card through the POC outcomes twice on 2026-11-16, step by step, asking at each step what goes in, what comes out and what the next run starts with.

The spec for a card settles the points listed for it and removes them here in the same pull request. A point that turns out to be a real trade-off goes to the developer as a question and becomes an ADR. A spec session that meets a new gap adds it here.

## Questions for the developer, each before its card

- **The work repo's list** (before its first card): which hosts its spec runs may reach (ADR 0059). With it goes what a refuse-list would be for. The address rule cannot tell a public address that is reachable, or answers, only because the request comes from the developer's network: a service behind a VPN with a public address, or one that admits the developer's address by a list. A run with `*` reaches such a host as the developer would, though without the developer's sign-ins. The developer has named none so far (card 12).
- **Actions under "needs you"** (the review-loop card): what the developer can do with such a card besides dropping it (ADR 0054, ADR 0016); what the retry becomes is settled: the developer's move makes the next run a first run (docs/settled.md, ADR 0016). What the number of send-backs becomes is settled: the developer's moves leave it, and approving a spec sets it to 0 (docs/settled.md, ADR 0054). Evidence from card 2: all three reviews had findings, and every fix held. Each fresh reviewer found something the last had not: a container left by a failed start, a network left on a cancelled context, a removal that cannot be repeated, and once a real hole in the seal. The third review brought the card to the developer for a fix of a few lines. The question should cover an action "fix this one finding and check only the fix", next to dropping the card.

ADR 0060, rule 4, says a session never gives the yes for a change to the workflow files, and the screen's API cannot tell a session on the same machine from the page, since only browsers send an Origin. The Git host can fail to fire automatic merging: on 2026-11-16, during an incident on the Git host, a pull request stood with automatic merging on and every requirement met, and did not merge. The core should notice such a pull request on a tick and ask the Git host to merge it directly, the path ADR 0049 already has. A second case on 2026-11-17, with no incident on the Git host's status page: pull request 7 had automatic merging on, the developer's approval and a passed check, and stood ready for five minutes. It merged within seconds of automatic merging being switched on a second time. So the core has two ways to deal with a pull request that is ready but still open: merge it directly, or switch automatic merging on again. The card that gives Kiln the app's key settles which, and after how long. A failure of an unreliable test on the Git host counts against the card as a send-back, like any failed check (2026-11-24). This contradicts the sentence on `TestSteps` under "Checks, one known unreliable case", which says not to count it against the card whose pull request it failed on: the core now counts it before anyone reads it. The card with the list of unreliable tests settles that. A pull request whose card is back in implement after a failed check keeps automatic merging on at the Git host: a check that the developer re-runs by hand and that passes then merges it while the card is in implement, and nothing notices that until the card is published again and finds everything in `main` already. After a hard kill of the core, the check result command can still be running while the next core runs it again, as with the publish command; a command that only reads copes. Republishing after a failed check pushes a commit that does not descend from the one before, so the developer's publish command must force-push to `card/<id>-<name>`, as the developer's send-back from the Git host already needs.
- **Checks:** how CPU time per check run is recorded on hosted runners (ADR 0031). The "no C code" step (ADR 0037) lets through a package made only of C that nothing imports, and a dependency that falls back to a stub without C; rejecting cgo files and packages with no Go files left would close both.
- **Checks, one known unreliable case** (for the same card, which has the list of unreliable tests): `TestSteps` in `internal/run` asserts that the scripted upstream sees exactly two requests per run. A third was seen on the Git host's runner on 2026-11-17 and 2026-11-18, in 2 check runs of 13, the second on pull request 11, whose change touches only the store. It was also seen once on the developer's machine, right after it woke from sleep. Each time Claude Code repeated a request after an `api_retry` event. On pull request 11 it was the run's first request, on a fresh connection, and Claude Code's session recorded "Connection dropped (ECONNRESET)", "The socket connection was closed unexpectedly", source `connection_retry`, 6 ms after the request reached the upstream. The upstream had answered without an error. Each time the proxy logged `ReverseProxy read error during body copy: … use of closed network connection`.
  - An investigation on 2026-11-18 reproduced the failure once in 114 runs like the test's, with the proxy held to a tenth of a CPU, and recorded the packets in the proxy's network namespace. The proxy writes the first bytes of the answer to the run. 110 µs later it resets its own connection to the upstream, with the rest of the answer unread, and then it closes the run's connection. No packet from the run or from outside comes before that.
  - So Claude Code did not cut and repeat its own request, and the engine's network did not reset the connection. The proxy also did not close because the run's connection went away: a cancelled request reads "context canceled", not the logged error.
  - The cause that fits is in Go's `net/http` (Go's issue 40747). The HTTP/1 server closes a request's body at the handler's first write of the answer. `ReverseProxy` gives the same body to the transport, which reads once more after the last byte when it speaks HTTP/1 to the upstream. If that read comes after the close, the transport closes its connection to the upstream, and the answer is cut off.
  - The scripted upstream speaks HTTP/1 and answers within a millisecond, which opens the gap. Towards Claude's API the transport speaks HTTP/2, which makes no such read for a request with a Content-Length, so real runs are not expected to meet it.
  - Card 10 turned the close off (`EnableFullDuplex` in `cmd/proxy`). A test of the proxy forces the order, and fails without the change.
  - Not shown: that the failures took this path. No real failure gave a stack trace, and the reproductions force the timing.
  - When the case fails again: read the test's output before anything else, do not re-run blindly, and do not count it against the card whose pull request it failed on.
  - A failure with the same signature means that the transport closed its connection to the upstream by another path. The signature is a repeated request, ECONNRESET, and that line in the proxy's log. The next step is a copy of the proxy that logs a stack trace whenever a connection to the upstream is closed. It is run in loops like the test's, or in a check run on the Git host, which is the developer's call.
  - A failure without that line in the proxy's log points away from the proxy.
- **Checks, the engine tests' images** (for the card that brings ADR 0031's rules, or a card of its own): since 2026-11-20, the toolchain image and Go's build cache come from caches that `main` fills. The images that the engine tests build themselves (proxy, run image with the 370 MB download of Claude Code, way out, the test upstreams) are still built from nothing on every run. Caching them changes the tests' builds in `internal/seal`, `internal/run` and `internal/tick`, or the Dockerfiles under `images/`, and needs a builder that can import cache on the runner. Measure first how the engine part's time splits, from the timestamps of a run's log. Since 2026-11-25 each engine package runs on a runner of its own, so its images are built once per package and job. A cache of them would go through the Git host's cache, with a builder that can import it.

## Notes for later cards

- **The review-loop card.** A review that sends a change back and a later review of the same card can propose the same problem twice. Nothing tells them apart, and each is kept (2026-11-24).
- **The start script.** `scripts/kiln-up` builds the program from `KILN_SOURCE` as it is. A source behind `main` gives a program that may be older than the store, which then refuses to start, or that updates itself at once. A source at a commit that is not in the copy gives a core that cannot tell whether `main` is past it, and never updates. The script warns about neither (2026-11-24).
- **The card that lets the settings change while the core runs.** A settings file is read again by every core at its start, also by the new core of an update. A file that the developer broke while the core ran makes that new core refuse to start, before it opens the store, and the update counts as failed. The previous program refuses the same file before it puts the store's copy back or turns automatic merging off, so merging stays on; its non-zero exit ends the launcher, and the update is blamed for the file. The store is as its copy, since neither core opened it (2026-11-25).
- **Relative paths under the launcher.** `--data`, `--repo` and `--page` given relative to `kiln launch`, or a relative `KILN_DATA` or `KILN_REPO` given to `scripts/kiln-up`, are made absolute by each core at its own start, from the launcher's directory as it is then. A directory removed or renamed while Kiln runs makes the next core, after a crash or at an update, miss them, and at an update that is a failed update. `--settings` is refused relative and made absolute by the script (2026-11-25).
- **The measures card (ADR 0042, rule 2).** Starting is not an intervention. A `start` after a dropped predecessor is a start that the developer had to make, and whether it counts is that card's call (2026-11-24).
- **The card that resumes a sent-back stage** (ADR 0053). Resume by the session's ID or the path to its record and never with `--fork-session`. A fork has a new `session_id` and restores the earlier totals as well, so the cost counted for it would be the whole conversation's (docs/settled.md, ADR 0053). Claude Code writes a session's totals into its record when the process exits normally; a session whose run was killed is not resumed (ADR 0053, rule 2).
- **The ceilings card.** A run's disk use has no bound. Measured on 2026-11-17 on the developer's container engine: `--storage-opt size=100M` is accepted and not enforced, and a run wrote 200 MiB. A bound on the logs alone does not bound the disk, and it would cut the complete record of a run (ADR 0038). A run's logs (`json-file`) have no `max-size`. The save's pack is held in memory on the developer's machine, so with no bound on a run's disk use, a large file that a run writes and does not ignore becomes a large pack (card 4's review). The budget flag does not count the totals a resumed session restores (docs/settled.md, ADR 0029). A spec run's subagents may run on another model than the run (Claude Code offers Explore and others). Its `result.json` holds the cost of the whole run (card 11).
- **The approval card.** Bidirectional control characters (U+202A to U+202E, U+2066 to U+2069) pass `Printable`. They are not escape sequences, but they can make the spec on the screen read otherwise than its text. Decide before a spec can be approved (card 11). A proposal's text becomes a card's text with "Make a card", and once the developer starts that card it is a spec run's instruction. Bidirectional control characters in it are shown as they are, like those in a spec (2026-11-24).
- **The approval card, and the stage cards.** A spec run may write other files to `/kiln/out`. They stay in `documents.tar` unread (card 11).
- **After the push card** (ADR 0040, ADR 0016). The push is built (docs/settled.md, ADR 0040), and renewing the credential no longer replaces the proxy. A run refused because the credential command printed a credential the upstream refuses, while the command itself succeeds, is run again at once, with no bound and no pause, each time for Claude Code's two to three minutes of retries (2026-11-24). A pause lasts as long as the core that found it: one left in the store by a core that stopped is ended, or kept with a new reason, by the next core's push at its start. The instance's entries are numbered apart from the cards' entries; one stream for both is the stream card's (ADR 0044, ADR 0055). The core keeps the proxy at its start only: a proxy that stops while the core runs is started again by the next core, and its runs' requests fail meanwhile. The developer changed ADR 0040's sentence on the push on 2026-11-23, both halves: it goes "through the container engine, into the proxy's container", "whenever a run's output shows that the credential was refused". Not done in the push card, each for a later decision: a length prefix on the push, so that a credential cut short in transit is told from a whole one; a renewal on a 503 from the upstream, as on a 401; and what to do about a run that prints retry events of a refused credential that never happened, which can make the core run the command at most once in ten seconds.
- **The standards card.** Three of card 2's four findings were of one kind, clean-up and repeating a step on code that drives the engine. Candidate for a written standard, so that implement has it before it writes code (ADR 0015, rule 3): a function that creates or removes something on the engine leaves nothing behind when it fails, is safe to repeat (ADR 0035), and a test shows both. Also decided by the developer on 2026-11-17: commit messages and pull request titles in Kiln's repo follow Conventional Commits (`type(scope): summary`, the scope optional), from card 3 on. With squash merging the pull request's title becomes the commit on `main`, so the rule covers both. It settles the format part of "who writes commit messages and the pull request's title and text" (ADR 0020, ADR 0028); who writes them stays open. It belongs with the written standards once they exist, and a format a tool can check is a check, not review (ADR 0015, rule 4). The Conventional Commits rule is in `CLAUDE.md` since card 11, until the written standards exist.
- **The MVP card that rebuilds placing and collecting for Kubernetes** (ADR 0038). The developer asked on 2026-11-17 for a container that holds the instance's copy of the repo in a volume, so that nothing of a working tree touches the disk of the developer's machine. For the POC the save's unpacking moved into a throwaway container instead (card 4). A volume that holds the copy is worth weighing at the MVP, with where saved and unpublished work is kept safe and how that container reaches the Git host.
- **The first UI card.** Modern Web Guidance, skills for coding agents on current web platform practice (Apache-2.0, stewarded by browser vendors and MDN), is worth trying. Runs are sealed, so it has to be in the repo or the run image, as part of the repo's Claude Code configuration, which is a protected place.
- **The visual design session.** Candidates for a short written standard for the UI: answer within about 400 ms, fewer choices, larger targets, familiar patterns, and less animation for what is used all day.
- **The API card.** A `Create` that is repeated after a kill writes a second card, because the caller cannot tell whether the first was written (card 6). A `POST /api/cards` repeated after a kill writes a second card, now with its predecessors too, as before (2026-11-24). The card settles how a repeat is recognised, for example with an identity for each request. The instance's data directory came with card 8 (`kiln core --data`). The API card removes `kiln card`, which stands in for the API until then, in the same pull request (ADR 0044).
- **The ceilings card.** The tick no longer follows a run to its end: since card 17 a follower beside it carries each run, and several are in flight at once. What is left is the time ceilings (ADR 0029), checked from the engine's facts (ADR 0035, rule 5) (card 8, card 17).
- **A run in flight across a core restarted with other flags.** A run's row holds the commit, the model and the effort, and not the proxy, the image or the repo, so those flags changed while a run is in flight are not carried over. The container's environment names the proxy it was created with, so a core restarted with another `--proxy` attaches the new proxy to the run's network and starts the run against the old name. The container keeps the image it was created with, while the save runs in the image of the core's `--image` then. A core with another `--repo` looks for the run's commit and branch there. Which card settles it is open (card 8, by the developer's decision of 2026-11-19).
- **A way out that stops in the middle of a run** is started again only when its run is carried again, after a restart of the core (card 12).
- **WebFetch needs `api.anthropic.com` on a list** other than `*`, because its safety check with Anthropic is kept: Claude Code sends it through the way out, and without an answer fetches nothing (card 12).
- **What a run sends** (ADR 0059). The way out counts the bytes of each connection, and the card's page marks a host to which a run sent more than 64 KiB (docs/settled.md, ADR 0059). A cap, or a pause of a run that sends more than a bound, is left for a later card. That card decides on evidence from these records: what Kiln's own spec runs and the work repo's send per host, and how often the mark shows on runs that only read. A killed way out loses the counts of the connections open then; a line written every few seconds for a long connection would bound that loss, and is left for the same card (2026-11-25).
- **The tick, a run's network removed from outside** (card 8's implementer, 2026-11-19): if something other than Kiln removes the network of a run that is in the store, the core does not remove the container, and attaching the proxy fails with "there is no network". Creating the network again would not help, since the engine records a container's network by its ID. Nothing in Kiln removes such a network. A run whose container never started is ended as failed after 5 minutes (docs/settled.md, ADR 0035). What stays open is a network removed while its container runs: after a restart of the core, attaching the proxy fails on every tick, and the run stays in flight. Whether the engine lets a network that a running container is attached to be removed without a `docker network disconnect` first was not checked (2026-11-24).
- **Runs that still hold a place** (2026-11-24): a container in a restart loop under a restart policy set outside Kiln alternates between restarting and running, so the bound of 5 minutes in one state never ends it; `RestartCount`, an engine fact, could bound it. A run whose container exited and whose collection or save fails on every tick (see "The work repo") holds a place as well. A stuck state that is not about one card, such as the proxy gone so that attaching it fails for every created run, uses up each card's retry; ADR 0016, rule 3, would pause the instance instead.
- **A repo whose run image is not built** (2026-11-25). A failed build of a repo's own images, or a reason that keeps it from starting, is printed on the core's output only; the screen shows the repo's cards waiting for a run with no reason. Showing it needs a state of the repo's own in the store and a line on the board.
- **A toolchain added while a run is in flight** (2026-11-25). The save of an implement run in flight uses `kiln-run-<repo>`, which only a start builds, so it waits until a card of the repo starts. The README says to add a toolchain while none of the repo's implement runs is in flight; the fix would be to save in the image of the run's own container.
- **Two instances on one engine** (2026-11-25) with a repo of the same name share `kiln-toolchain-<repo>` and `kiln-run-<repo>`, and rebuild them in turn when their Dockerfiles or layers differ. They also share `kiln-cache-<repo>`, `kiln-fill-<repo>` and the cache volumes `kiln-cache-<repo>-<digest>`: a fill of one removes the other's proof, and the other then fills again (2026-11-26).
- **Old cache volumes stay** (2026-11-26). Each change of a repo's cache's Dockerfile, inputs or toolchain fills a new volume, and the old one stays, about as large as the cache, until the developer removes it (README). Removing a repo's cache volumes that no container uses and whose digest is not the current one is the next card's.
- **A fill has no ceiling** (2026-11-26). A fill that hangs holds the repo's runs until the developer removes `kiln-fill-<repo>`. A toolchain build has none either.
- **A cache taken out of the settings** (2026-11-26) leaves its volumes, `kiln-fill-<repo>` and `kiln-cache-<repo>` on the engine.
- **The fill's command is not checked** (2026-11-26). A cache Dockerfile without a `CMD` of its own runs the toolchain's, often `bash`, which exits 0 at once with an empty cache; the runs' offline restores then fail.
- **A fill found running by a later core** (2026-11-26) is removed and started again, which loses its progress. Picking it up would take more code.
- **A cache whose digest comes back** (2026-11-26), as after a lock file reverted, is filled again into the volume of that name, since the proof container has moved on. While a container of an earlier run still uses that volume, the engine refuses its removal: the fill fails, is printed, and is tried again a minute later, until that run's container is gone.
- **A repo whose `cpus` is above the engine's count** (2026-11-26). Like a run image that is not built, it is said on the core's output only, and the board shows the card waiting for a run with no reason. The same card that gives a repo a state of its own would show it.
- **Two instances on one engine** (2026-11-26). Their runs count each other's cpusets, but the lock is per process, so creates at the same moment can share CPUs. The same holds for `kiln run` by hand.
- **The proxy, if it ever serves another client** (card 10's review, 2026-11-18; not a finding): since the proxy lets a request's body be read while the answer is passed on, an answer to a request whose body the upstream did not read (over 256 KB), and a 502 because the upstream is down, go out as keep-alive, and the proxy then closes the connection. Before, such an answer carried `Connection: close`. A hand-written client that sends its next request on that connection at once gets an EOF: every time when the upstream is down, once in 50 tries when the upstream answers early. Node's and Bun's `fetch` did not fail in 20 tries at each of 0, 5, 50 and 300 ms between requests, so Claude Code is not affected.
- **When Kiln builds its own cards.** A sealed implement run cannot add a Go module, because it has no network and the toolchain image carries only the modules of `go.mod` as it was built (card 6, ADR 0057). How a card whose spec needs a new module gets it is open. A module whose version changes is settled (docs/settled.md, ADR 0057); how a new module gets its entry and its files is still open.
- **The card that shows a run to the developer.** A `kiln run` that is started again on a run that has already ended collects, saves, records and removes without printing a line. It should say what it did: the saved commit and branch, or "no change", and where the record is (card 5).
- **The launcher card.** Unexplained, from the first real run on 2026-11-17 (card 5): on the developer's machine the freshly built `kiln` program was killed twice within a second of starting, and ran normally a few minutes later. Its signature was valid, the antivirus reported nothing, and writing a program over an existing one did not reproduce it. If it happens again with the launcher's builds (ADR 0036, ADR 0037), this card has to find the cause. Until 2026-11-20 the README's build wrote the new program over the old file in place (`>kiln`). Apple's "Updating Mac Software" says that this can make the program crash with "Code Signature Invalid", and that a new file renamed over the old one avoids it. The README now does the latter. The launcher now prints each core's end with its signal: a first start that is killed ends the launcher with that line, and the cause of the kill of 2026-11-17 is still open.
- **The stage cards.** A target repo's settings may change the effort, through `CLAUDE_CODE_EFFORT_LEVEL`, or the model, and a run's output shows only the model (card 5, ADR 0030). Whether a repo's project settings can set either is unclear; Kiln's repo has no `.claude/settings.json`.
- **The review card.** Every run's `/work` is a local repository with a baseline commit, and a parent at where the card's branch left `main` when the run starts elsewhere (docs/settled.md, ADR 0038), so `git diff` shows what the run itself changes and `git diff HEAD~1` the card's whole change. What else a reviewing run needs of a diff base is open (2026-11-25). A run can also make its save fail every time, as the note on the work repo below says.
- **The work repo.** Submodules are refused (card 5), and attributes that rewrite content on `add` are applied by the save. A run can make its save fail every time: Git refuses paths such as `.GIT/x`, `git~1/x` or `.git /x`, and a symlinked `.gitmodules`, so `add -A` in the save container exits with an error on every repeat. Nothing is lost, because the run's container stays, but that run's work cannot be saved. The save's error also carries 20 raw lines of the save's output, so file names a run chose reach the terminal (card 4's review).
- **Things to read before writing Kiln's own, saved by the developer on 2026-11-17.** None is installed; a sealed run can only use what is in the repo's Claude Code configuration or the run image, pinned, with a dependency entry (ADR 0025, ADR 0051).
  - **The standards card and the visual design session:** the `learn-taste` skill (github.com/emilkowalski/skills, read at commit 64eb3de) turns a developer's design corrections into written rules. Worth borrowing: every rule traces to something the developer said and carries its reason; a rule a tool can check becomes a check (as ADR 0015, rule 4); a rule is written at the narrowest level that prevents the mistake on the next component, for an agent that was not there; it proposes and stops. It reads a conversation, which a headless run does not have; Kiln's corrections are rejected specs, review findings and interventions. `claude-md-management` in Anthropic's plugin directory (github.com/anthropics/claude-plugins-official) does a similar job for `CLAUDE.md`.
  - **The review-loop card:** the `code-review` plugin in the same directory reviews with several agents and filters findings by a confidence score. Read it before writing Kiln's review instruction (ADR 0056), for the filter, and weigh it against the cost of a review.
  - **The first UI card:** `frontend-design` from the same directory, next to Modern Web Guidance.
  - **When the code has grown:** `gopls-lsp`, which gives an agent Go's language server; it needs `gopls` in the toolchain image.
- **The event stream card, and any card that changes `GET /api/board`.** A page left open when such a card merges is the old page. It reloads only if `GET /api/board` still answers its 2-second ask with `build`. So the path and the field stay until no page from before can be open, or the new page's build is carried somewhere the old page reads. Pages opened before this card's merge have no check at all and need one reload by hand.
- **Images left behind by the update.** Each update that rebuilds an image leaves the previous version's image untagged (`<none>`) in the engine once the new core has promoted its own, while runs in flight may still use it. The tags of a build that never handed over stay until the next update. Nothing removes the untagged images. `docker image ls --filter dangling=true` lists them; `docker image prune` removes every untagged image of the engine, also those not Kiln's. How much disk an update leaves is not measured; the base layers are shared. A rebuild of `kiln-toolchain-<repo>`, `kiln-run-<repo>` or `kiln-cache-<repo>`, a repo's own images, leaves the previous image untagged too (2026-11-25, `kiln-cache-<repo>` 2026-11-26).
- **The CLAUDE.md card.** Card 11 brought the file with three rules: the docs to read, Conventional Commits and that the repo is public. Two things are left: the check command, which comes first, and the sentence that tells the agent it owns the codebase, which stays an experiment to measure against send-backs, not a default.
- **The measures.** The developer's approval of a protected path on the Git host is an intervention (docs/settled.md, ADR 0006). The core does not see it yet, so the board's count leaves it out and the strip's title says so; the card that makes the core see that approval adds it to the count. The phase list's third measure counts only the follow-up fixes the developer names when writing a card (docs/settled.md, ADR 0007); finding one by itself, from commit messages or the files changed, is left to a later card (2026-11-24). Turning automatic merging on is an entry of the instance and is counted on no card. "Proposals made" counts every proposal kept, malformed ones included (2026-11-24).
- **MVP item 1, what is still missing** (2026-11-25). The card carries the work item number and hands it to the publish command. Two pieces are still open.
  - The publish command for Azure DevOps. It is the developer's, outside the repo, and links `$KILN_WORK_ITEM`, for example with `az repos pr create --work-items`, or `az repos pr work-item add` on a pull request that exists.
  - The observing card. The core sees a merge from the copy's `main`, squash merges included (docs/settled.md, ADR 0027), as long as the copy's `origin` is the Azure repo and fetches without a prompt. It does not notice an abandoned pull request, nor one Azure DevOps reports as unable to merge. Both need the developer's move today, as on GitHub.
  - A number changed by a later approval is handed to the command on the next publishing, and the old link stays on the pull request.
