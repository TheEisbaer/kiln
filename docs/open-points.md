# Open points

Points the decisions do not settle yet, listed by the card that has to settle them. They come from tracing one card through the POC outcomes twice on 2026-11-16, step by step, asking at each step what goes in, what comes out and what the next run starts with.

The spec for a card settles the points listed for it and removes them here in the same pull request. A point that turns out to be a real trade-off goes to the developer as a question and becomes an ADR. A spec session that meets a new gap adds it here.

## Questions for the developer, each before its card

- **The work repo's list** (before its first card): which hosts its spec runs may reach (ADR 0059). With it goes what a refuse-list would be for. The address rule cannot tell a public address that is reachable, or answers, only because the request comes from the developer's network: a service behind a VPN with a public address, or one that admits the developer's address by a list. A run with `*` reaches such a host as the developer would, though without the developer's sign-ins. The developer has named none so far (card 12).
- **Actions under "needs you"** (the review-loop card): what the developer can do with such a card besides dropping it, and what the card's two facts become afterwards (ADR 0054). Evidence from card 2: all three reviews had findings, and every fix held. Each fresh reviewer found something the last had not: a container left by a failed start, a network left on a cancelled context, a removal that cannot be repeated, and once a real hole in the seal. The third review brought the card to the developer for a fix of a few lines. The question should cover an action "fix this one finding and check only the fix", next to dropping the card.
- **Updates beyond the core** (the automatic-update card): who rebuilds and restarts the proxy and the run image after a merge (ADR 0034, ADR 0039); what the old core may still do after it has copied the store (ADR 0036); whether an unreachable Git host makes an update count as failed. A merge that changes `go.mod` needs a rebuilt toolchain image and run image before a run or a build can use the new module (ADR 0057).

The cost a resumed run reports (ADR 0029, ADR 0053): the ceilings card.
- **Spec stage:** rejecting a spec with reasons, and answering its questions (ADR 0021, ADR 0053); the fields of a card, of which the store has only the text so far, and the lines of a spec that the core reads (ADR 0030, ADR 0051): the spec-stage card adds the fields the core reads. The core reads the lines `Pull request title:` since 2026-11-20 and `Model for implement:` since 2026-11-23; the others stay with the spec-stage card. - **Review loop:** what a send-back round and the next reviewer receive; whether a killed run's partial work is the saved state its retry starts from (ADR 0013, ADR 0016). What implement receives after a failed check on the Git host, and how the core gets that output. How a run reports that the spec cannot be built as written (ADR 0012).
- **Failures:** how a pause ends and what happens to runs in flight; a credential that expires while the core is down pauses the instance and does not use up a card's retry (ADR 0016, ADR 0040). A run in flight across an update that changes the pinned Claude Code, whose output the new core was not tested with (ADR 0039); event numbers after a copy of the store is put back (ADR 0036, ADR 0044): they stay open, and the spec of the stream's card settles them.
- **Publishing:** card 19 settled who writes the pull request's title and text (ADR 0020, ADR 0028), what happens when the publishing step fails (the card needs you, and the developer publishes again), and the card branch pattern: saves stay on `kiln/card-<id>` in the instance's copy, and a card is published on `card/<id>-<name>` (docs/settled.md, ADR 0017, ADR 0052). Still open: Kiln holding the app's key itself, which today the developer's publish command holds outside the repo (ADR 0052, rule 4); noticing a pull request closed without a merge, and one the Git host reports as unable to merge or with a failed check (ADR 0012, rule 2), which today needs the developer's move; what the one switch does to pull requests that already have automatic merging on (ADR 0006); removing a card's branches after the merge. After a hard kill of the core, or a closed terminal, the publish command can still be running when the next core runs it again for the same card; only the command copes with that today. ADR 0060, rule 4, says a session never gives the yes for a change to the workflow files, and the screen's API cannot tell a session on the same machine from the page, since only browsers send an Origin. The Git host can fail to fire automatic merging: on 2026-11-16, during an incident on the Git host, a pull request stood with automatic merging on and every requirement met, and did not merge. The core should notice such a pull request on a tick and ask the Git host to merge it directly, the path ADR 0049 already has. A second case on 2026-11-17, with no incident on the Git host's status page: pull request 7 had automatic merging on, the developer's approval and a passed check, and stood ready for five minutes. It merged within seconds of automatic merging being switched on a second time. So the core has two ways to deal with a pull request that is ready but still open: merge it directly, or switch automatic merging on again. The card that gives Kiln the app's key settles which, and after how long.
- **Checks:** how CPU time per check run is recorded on hosted runners (ADR 0031). The "no C code" step (ADR 0037) lets through a package made only of C that nothing imports, and a dependency that falls back to a stub without C; rejecting cgo files and packages with no Go files left would close both. The engine tests run on every pull request on the Git host's runner, whatever it changes, and the check has grown from 45 seconds (card 1) to 2 minutes 14 seconds (card 3); card 4's spec expects 3.5 to 4.5 minutes. ADR 0031, rule 3, says that unchanged code is not re-tested and that a card pays for what it touches. The card that brings ADR 0031's rules settles whether a pull request that touches neither the seal, the run's steps nor the images skips the engine tests, and who decides that, since the workflow file and `check/` are protected.
- **Checks, one known unreliable case** (for the same card, which has the list of unreliable tests): `TestSteps` in `internal/run` asserts that the scripted upstream sees exactly two requests per run. A third was seen on the Git host's runner on 2026-11-17 and 2026-11-18, in 2 check runs of 13, the second on pull request 11, whose change touches only the store. It was also seen once on the developer's machine, right after it woke from sleep. Each time Claude Code repeated a request after an `api_retry` event. On pull request 11 it was the run's first request, on a fresh connection, and Claude Code's session recorded "Connection dropped (ECONNRESET)", "The socket connection was closed unexpectedly", source `connection_retry`, 6 ms after the request reached the upstream. The upstream had answered without an error. Each time the proxy logged `ReverseProxy read error during body copy: … use of closed network connection`.
  - An investigation on 2026-11-18 reproduced the failure once in 114 runs like the test's, with the proxy held to a tenth of a CPU, and recorded the packets in the proxy's network namespace. The proxy writes the first bytes of the answer to the run. 110 µs later it resets its own connection to the upstream, with the rest of the answer unread, and then it closes the run's connection. No packet from the run or from outside comes before that.
  - So Claude Code did not cut and repeat its own request, and the engine's network did not reset the connection. The proxy also did not close because the run's connection went away: a cancelled request reads "context canceled", not the logged error.
  - The cause that fits is in Go's `net/http` (Go's issue 40747). The HTTP/1 server closes a request's body at the handler's first write of the answer. `ReverseProxy` gives the same body to the transport, which reads once more after the last byte when it speaks HTTP/1 to the upstream. If that read comes after the close, the transport closes its connection to the upstream, and the answer is cut off.
  - The scripted upstream speaks HTTP/1 and answers within a millisecond, which opens the gap. Towards Claude's API the transport speaks HTTP/2, which makes no such read for a request with a Content-Length, so real runs are not expected to meet it.
  - Card 10 turned the close off (`EnableFullDuplex` in `cmd/proxy`). A test of the proxy forces the order, and fails without the change.
  - Not shown: that the failures took this path. No real failure gave a stack trace, and the reproductions force the timing.
  - When the case fails again: read the test's output before anything else, do not re-run blindly, and do not count it against the card whose pull request it failed on.
  - A failure with the same signature means that the transport closed its connection to the upstream by another path. The signature is a repeated request, ECONNRESET, and that line in the proxy's log. The next step is a copy of the proxy that logs a stack trace whenever a connection to the upstream is closed. It is run in loops like the test's, or in a check run on the Git host, which is the developer's call.
  - A failure without that line in the proxy's log points away from the proxy.
- **Checks, the engine tests' images** (for the card that brings ADR 0031's rules, or a card of its own): since 2026-11-20, the toolchain image and Go's build cache come from caches that `main` fills. The images that the engine tests build themselves (proxy, run image with the 370 MB download of Claude Code, way out, the test upstreams) are still built from nothing on every run. Caching them changes the tests' builds in `internal/seal`, `internal/run` and `internal/tick`, or the Dockerfiles under `images/`, and needs a builder that can import cache on the runner. Measure first how the engine part's time splits, from the timestamps of a run's log.

## Notes for later cards

- **The ceilings card.** A run's disk use has no bound. Measured on 2026-11-17 on the developer's container engine: `--storage-opt size=100M` is accepted and not enforced, and a run wrote 200 MiB. A bound on the logs alone does not bound the disk, and it would cut the complete record of a run (ADR 0038). A run's logs (`json-file`) have no `max-size`. The save's pack is held in memory on the developer's machine, so with no bound on a run's disk use, a large file that a run writes and does not ignore becomes a large pack (card 4's review). A resumed run reports the cost of the whole conversation (Claude Code 2.1.325, ADR 0029, ADR 0053). A spec run's subagents may run on another model than the run (Claude Code offers Explore and others). Its `result.json` holds the cost of the whole run (card 11).
- **The approval card.** Bidirectional control characters (U+202A to U+202E, U+2066 to U+2069) pass `Printable`. They are not escape sequences, but they can make the spec on the screen read otherwise than its text. Decide before a spec can be approved (card 11).
- **The approval card, and the stage cards.** A spec run may write other files to `/kiln/out`. They stay in `documents.tar` unread (card 11).
- **After the push card** (ADR 0040, ADR 0016). The push is built (docs/settled.md, ADR 0040), and renewing the credential no longer replaces the proxy. What is left: a run that ended because the upstream refused the credential goes to "needs you" and is not run again by itself, which is the retry card's, with ADR 0016's rules. A pause lasts as long as the core that found it: one left in the store by a core that stopped is ended, or kept with a new reason, by the next core's push at its start. The instance's entries are numbered apart from the cards' entries; one stream for both is the stream card's (ADR 0044, ADR 0055). The core keeps the proxy at its start only: a proxy that stops while the core runs is started again by the next core, and its runs' requests fail meanwhile. ADR 0040 says the push goes "over a port that is open only on the developer's machine itself"; it has no port at all, and the sentence is the developer's to change.
- **The standards card.** Three of card 2's four findings were of one kind, clean-up and repeating a step on code that drives the engine. Candidate for a written standard, so that implement has it before it writes code (ADR 0015, rule 3): a function that creates or removes something on the engine leaves nothing behind when it fails, is safe to repeat (ADR 0035), and a test shows both. Also decided by the developer on 2026-11-17: commit messages and pull request titles in Kiln's repo follow Conventional Commits (`type(scope): summary`, the scope optional), from card 3 on. With squash merging the pull request's title becomes the commit on `main`, so the rule covers both. It settles the format part of "who writes commit messages and the pull request's title and text" (ADR 0020, ADR 0028); who writes them stays open. It belongs with the written standards once they exist, and a format a tool can check is a check, not review (ADR 0015, rule 4). The Conventional Commits rule is in `CLAUDE.md` since card 11, until the written standards exist.
- **The MVP.** Kiln's layer needs a few things from a toolchain image, namely `curl`, `sha256sum`, `useradd`, `sh` and a free uid 1000. The save needs `git`, `find` and `chmod` from it as well (card 4).
- **The MVP card that rebuilds placing and collecting for Kubernetes** (ADR 0038). The developer asked on 2026-11-17 for a container that holds the instance's copy of the repo in a volume, so that nothing of a working tree touches the disk of the developer's machine. For the POC the save's unpacking moved into a throwaway container instead (card 4). A volume that holds the copy is worth weighing at the MVP, with where saved and unpublished work is kept safe and how that container reaches the Git host.
- **The first UI card.** Modern Web Guidance, skills for coding agents on current web platform practice (Apache-2.0, stewarded by browser vendors and MDN), is worth trying. Runs are sealed, so it has to be in the repo or the run image, as part of the repo's Claude Code configuration, which is a protected place.
- **The visual design session.** Candidates for a short written standard for the UI: answer within about 400 ms, fewer choices, larger targets, familiar patterns, and less animation for what is used all day.
- **The API card.** A `Create` that is repeated after a kill writes a second card, because the caller cannot tell whether the first was written (card 6). The card settles how a repeat is recognised, for example with an identity for each request. The instance's data directory came with card 8 (`kiln core --data`). The API card removes `kiln card`, which stands in for the API until then, in the same pull request (ADR 0044).
- **The retry card.** A second run of a card now starts from the branch's tip: an implement run starts from the tip of `kiln/card-<id>` when the branch exists, and a review run always does (card 14). A spec run still starts from the head of `main`, also for a card sent back to spec, which keeps its branch: a run that saves nothing does not judge where the branch is (card 17).
- **The limits and ceilings cards.** The tick no longer follows a run to its end: since card 17 a follower beside it carries each run, and several are in flight at once. What is left is the time ceilings (ADR 0029), checked from the engine's facts (ADR 0035, rule 5) (card 8, card 17). A run left alone, its container paused or dead, and a run whose way out was gone before it started both count as in flight in the store, so each holds one of the `--runs` places until the developer acts; with `--runs 1` that holds every card (card 17's review).
- **The automatic-update card.** A copied store has the same instance. The lock is per directory, so the old core must have stopped before the new one ticks. A copy that is put back makes the sweep remove runs started after the copy (ADR 0035, rule 4; card 8).
- **A run in flight across a core restarted with other flags.** A run's row holds the commit, the model and the effort, and not the proxy, the image or the repo, so those flags changed while a run is in flight are not carried over. The container's environment names the proxy it was created with, so a core restarted with another `--proxy` attaches the new proxy to the run's network and starts the run against the old name. The container keeps the image it was created with, while the save runs in the image of the core's `--image` then. A core with another `--repo` looks for the run's commit and branch there. Which card settles it is open (card 8, by the developer's decision of 2026-11-19).
- **A container that is dead or paused.** The tick leaves a run whose container is dead, paused or restarting alone, and prints it on every tick, until a card decides what it is (card 8). The same holds for a run with a list whose way out is gone before the run has started: it stays in flight, said on every tick (card 12).
- **A way out that stops in the middle of a run** is started again only when its run is carried again, after a restart of the core (card 12).
- **WebFetch needs `api.anthropic.com` on a list** other than `*`, because its safety check with Anthropic is kept: Claude Code sends it through the way out, and without an answer fetches nothing (card 12).
- **The tick, a run's network removed from outside** (card 8's implementer, 2026-11-19): if something other than Kiln removes the network of a run that is in the store, the core does not remove the container, attaching the proxy fails on every tick with "there is no network", and the run stays in flight. Creating the network again would not help, since the engine records a container's network by its ID. Nothing in Kiln removes such a network.
- **The tick, runs that are kept for ever** (card 8's last review, 2026-11-19; accepted by the developer for now): since nothing in the core removes the container of a run that is in the store, two states fail on every tick and never end. One is the run's network removed from outside while its container never started, which the note above describes. The other is a container that the engine refuses to start, for example with a broken run image or with limits the virtual machine no longer allows: each tick places the files again, and the start fails again. The printed error does not say what to do. The way out by hand: remove the run's container, and the next tick ends the run as failed, with the card under "needs you". A rule that ends such a run by itself belongs to the retry card (ADR 0016). Two more states are caused by a hand on the data directory, and nothing is built for either:
  - **A run's instruction removed.** If a run is in the store and its `instructions/<run>.md` was removed, and the core was rebuilt with another instruction in between, the tick writes the new text. The run's label `kiln.instruction` then refuses it on every tick, and the run stays in flight (card 11).
  - **A recorded run's `documents.tar` removed or unreadable.** A file that cannot be opened or read from the disk is tried again on every tick, so such a run stays in flight as well. A damaged archive does not keep it: the card goes under "needs you" (card 11).
- **The proxy, if it ever serves another client** (card 10's review, 2026-11-18; not a finding): since the proxy lets a request's body be read while the answer is passed on, an answer to a request whose body the upstream did not read (over 256 KB), and a 502 because the upstream is down, go out as keep-alive, and the proxy then closes the connection. Before, such an answer carried `Connection: close`. A hand-written client that sends its next request on that connection at once gets an EOF: every time when the upstream is down, once in 50 tries when the upstream answers early. Node's and Bun's `fetch` did not fail in 20 tries at each of 0, 5, 50 and 300 ms between requests, so Claude Code is not affected.
- **When Kiln builds its own cards.** A sealed implement run cannot add a Go module, because it has no network and the toolchain image carries only the modules of `go.mod` as it was built (card 6, ADR 0057). How a card whose spec needs a new module gets it is open.
- **The card that shows a run to the developer.** A `kiln run` that is started again on a run that has already ended collects, saves, records and removes without printing a line. It should say what it did: the saved commit and branch, or "no change", and where the record is (card 5).
- **The launcher card.** Unexplained, from the first real run on 2026-11-17 (card 5): on the developer's machine the freshly built `kiln` program was killed twice within a second of starting, and ran normally a few minutes later. Its signature was valid, the antivirus reported nothing, and writing a program over an existing one did not reproduce it. If it happens again with the launcher's builds (ADR 0036, ADR 0037), this card has to find the cause. Until 2026-11-20 the README's build wrote the new program over the old file in place (`>kiln`). Apple's "Updating Mac Software" says that this can make the program crash with "Code Signature Invalid", and that a new file renamed over the old one avoids it. The README now does the latter.
- **The stage cards.** A target repo's settings may change the effort, through `CLAUDE_CODE_EFFORT_LEVEL`, or the model, and a run's output shows only the model (card 5, ADR 0030). Whether a repo's project settings can set either is unclear; Kiln's repo has no `.claude/settings.json`.
- **The review card.** A run has no `.git` and no diff base; what a reviewing run needs of either is open. A run can also make its save fail every time, as the note on the work repo below says.
- **The work repo.** Submodules are refused (card 5), and attributes that rewrite content on `add` are applied by the save. A run can make its save fail every time: Git refuses paths such as `.GIT/x`, `git~1/x` or `.git /x`, and a symlinked `.gitmodules`, so `add -A` in the save container exits with an error on every repeat. Nothing is lost, because the run's container stays, but that run's work cannot be saved. The save's error also carries 20 raw lines of the save's output, so file names a run chose reach the terminal (card 4's review).
- **Things to read before writing Kiln's own, saved by the developer on 2026-11-17.** None is installed; a sealed run can only use what is in the repo's Claude Code configuration or the run image, pinned, with a dependency entry (ADR 0025, ADR 0051).
  - **The standards card and the visual design session:** the `learn-taste` skill (github.com/emilkowalski/skills, read at commit 64eb3de) turns a developer's design corrections into written rules. Worth borrowing: every rule traces to something the developer said and carries its reason; a rule a tool can check becomes a check (as ADR 0015, rule 4); a rule is written at the narrowest level that prevents the mistake on the next component, for an agent that was not there; it proposes and stops. It reads a conversation, which a headless run does not have; Kiln's corrections are rejected specs, review findings and interventions. `claude-md-management` in Anthropic's plugin directory (github.com/anthropics/claude-plugins-official) does a similar job for `CLAUDE.md`.
  - **The review-loop card:** the `code-review` plugin in the same directory reviews with several agents and filters findings by a confidence score. Read it before writing Kiln's review instruction (ADR 0056), for the filter, and weigh it against the cost of a review.
  - **The first UI card:** `frontend-design` from the same directory, next to Modern Web Guidance.
  - **When the code has grown:** `gopls-lsp`, which gives an agent Go's language server; it needs `gopls` in the toolchain image.
- **The event stream card, and any card that changes `GET /api/board`.** A page left open when such a card merges is the old page. It reloads only if `GET /api/board` still answers its 2-second ask with `build`. So the path and the field stay until no page from before can be open, or the new page's build is carried somewhere the old page reads. Pages opened before this card's merge have no check at all and need one reload by hand.
- **The CLAUDE.md card.** Card 11 brought the file with three rules: the docs to read, Conventional Commits and that the repo is public. Two things are left: the check command, which comes first, and the sentence that tells the agent it owns the codebase, which stays an experiment to measure against send-backs, not a default.
