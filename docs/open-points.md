# Open points

Points the decisions do not settle yet, listed by the card that has to settle them. They come from tracing one card through the POC outcomes twice on 2026-11-16, step by step, asking at each step what goes in, what comes out and what the next run starts with.

The spec for a card settles the points listed for it and removes them here in the same pull request. A point that turns out to be a real trade-off goes to the developer as a question and becomes an ADR. A spec session that meets a new gap adds it here.

## Questions for the developer, each before its card

- **Network for research** (the spec-stage card): which hosts a run may reach, and whether a spec run may read the web for its research (ADR 0009, ADR 0017).
- **Actions under "needs you"** (the review-loop card): what the developer can do with such a card besides dropping it, and what the card's two facts become afterwards (ADR 0054). Evidence from card 2: all three reviews had findings, and every fix held. Each fresh reviewer found something the last had not: a container left by a failed start, a network left on a cancelled context, a removal that cannot be repeated, and once a real hole in the seal. The third review brought the card to the developer for a fix of a few lines. The question should cover an action "fix this one finding and check only the fix", next to dropping the card.
- **Updates beyond the core** (the automatic-update card): who rebuilds and restarts the proxy and the run image after a merge (ADR 0034, ADR 0039); what the old core may still do after it has copied the store (ADR 0036); whether an unreachable Git host makes an update count as failed. A merge that changes `go.mod` needs a rebuilt toolchain image and run image before a run or a build can use the new module (ADR 0057).

## Settled in the spec of the card that first needs them

- **Runs:** which commit a card's first run starts from, and how the merged Claude Code configuration is laid over a card branch (ADR 0010, ADR 0025): the stage cards. The base of "what the card changed" (ADR 0015): the review card. How a finished run is told from a failed one when its result is missing or the engine killed it for memory (ADR 0016): the retry card, which gets the facts in a run's `result.json`. How long a run's record is kept (ADR 0032, ADR 0053): the tick card, which puts runs' records into the store. What happens to changes a spec or review run made to its working tree: the stage cards. Who enforces the advisor's "at most twice" (ADR 0030): the first card whose runs use the advisor. The cost a resumed run reports (ADR 0029, ADR 0053): the ceilings card.
- **Spec stage:** rejecting a spec with reasons, and answering its questions (ADR 0021, ADR 0053); the fields of a card, of which the store has only the text so far, and the lines of a spec that the core reads (ADR 0030, ADR 0051): the spec-stage card adds the fields the core reads. How the developer changes the proposed model at approval.
- **Review loop:** what a send-back round and the next reviewer receive; whether a killed run's partial work is the saved state its retry starts from (ADR 0013, ADR 0016). What implement receives after a failed check on the host, and how the core gets that output. How a run reports that the spec cannot be built as written (ADR 0012).
- **Failures:** how a pause ends and what happens to runs in flight; a credential that expires while the core is down pauses the instance and does not use up a card's retry (ADR 0016, ADR 0040). A run in flight across an update that changes the pinned Claude Code, whose output the new core was not tested with (ADR 0039); event numbers after a copy of the store is put back (ADR 0036, ADR 0044): they stay open, and the spec of the stream's card settles them.
- **Publishing:** who writes commit messages and the pull request's title and text (ADR 0020, ADR 0028), whose format is settled (the standards card, below); failures of steps that are not runs, such as a push; where the app's key lives; what the one switch does to pull requests that already have automatic merging on (ADR 0006); removing a card branch after the merge. The host can fail to fire automatic merging: on 2026-11-16, during an incident on the host, a pull request stood with automatic merging on and every requirement met, and did not merge. The core should notice such a pull request on a tick and ask the host to merge it directly, the path ADR 0049 already has. A second case on 2026-11-17, with no incident on the host's status page: pull request 7 had automatic merging on, the developer's approval and a passed check, and stood ready for five minutes. It merged within seconds of automatic merging being switched on a second time. So the core has two ways to deal with a pull request that is ready but still open: merge it directly, or switch automatic merging on again. The publishing card settles which, and after how long.
- **Checks:** how CPU time per check run is recorded on hosted runners (ADR 0031). The "no C code" step (ADR 0037) lets through a package made only of C that nothing imports, and a dependency that falls back to a stub without C; rejecting cgo files and packages with no Go files left would close both. The engine tests run on every pull request on the host's runner, whatever it changes, and the check has grown from 45 seconds (card 1) to 2 minutes 14 seconds (card 3); card 4's spec expects 3.5 to 4.5 minutes. ADR 0031, rule 3, says that unchanged code is not re-tested and that a card pays for what it touches. The card that brings ADR 0031's rules settles whether a pull request that touches neither the seal, the run's steps nor the images skips the engine tests, and who decides that, since the workflow file and `check/` are protected.
- **Checks, one known unreliable case** (for the same card, which has the list of unreliable tests): `TestSteps` in `internal/run` asserts that the scripted upstream sees exactly two requests per run. On 2026-11-17 one case of 34 saw a third on the host's runner, and the check failed; ten further runs of the same check on 2026-11-18 all passed. Reproduced once on the developer's machine, in another case, right after the machine woke from sleep: the third request is Claude Code repeating its second request after the answer was cut off 7 ms in. The upstream wrote "broken pipe", the proxy logged that its connection to the upstream was closed, which it does when the connection from the run goes away, and the run's output has an `api_retry` event. Not known: whether Claude Code cut its own request or the connection between the run and the proxy was reset. The upstream and the test's reading of its log are ruled out, and so are a request of Claude Code's own at the end of a session and the point at which a long shell call becomes a background task. The developer decided on 2026-11-18 to merge and observe. The test now explains such a failure by itself (each request with its time and connection, the run's unusual events, the error Claude Code's session records behind a retry, the proxy's log). When it fails this way again: read that output before anything else, do not re-run blindly, and do not count it against the card whose pull request it failed on. If the error is a reset between the run and the proxy, it is Kiln's to fix; if Claude Code cuts and repeats its own request, the assertion should count a repeated request as one conversation.
- **Checks, where the time goes and what a cache would take** (for the same card): on card 3's check run of 2 minutes 8 seconds the tests themselves took about 10 seconds. The rest was building from nothing on a fresh runner: pulling the Go image and building the toolchain image (25 s), format, vet, the build for macOS and the small tests (23 s), compiling the engine tests (10 s), and the run test's setup with the proxy, upstream and run images and the probe (about 58 s, of which the 370 MB download of Claude Code is the largest part). The Go standard library is compiled from cold about five times. The host has a cache for workflows (10 GB per repo, entries unused for 7 days are removed) and Docker has a layer cache backend for it. Read on 2026-11-17: a cache made by a pull request's run can only be restored by re-runs of that pull request, so a shared cache has to be made by a run on `main`, and Kiln's workflow runs on pull requests only. A cache therefore needs a second trigger in the workflow file, which is the developer's own pull request, and changes to `check/in-image` and the image definitions. Cache contents are not signed; one made on `main` is written by merged code only. The developer decided on 2026-11-17 to leave this until the card that brings ADR 0031's rules.

## Notes for later cards

- **The ceilings card.** A run's disk use has no bound. Measured on 2026-11-17 on the developer's container engine: `--storage-opt size=100M` is accepted and not enforced, and a run wrote 200 MiB. A bound on the logs alone does not bound the disk, and it would cut the complete record of a run (ADR 0038). A run's logs (`json-file`) have no `max-size`. The save's pack is held in memory on the developer's machine, so with no bound on a run's disk use, a large file that a run writes and does not ignore becomes a large pack (card 4's review). A resumed run reports the cost of the whole conversation (Claude Code 2.1.325, ADR 0029, ADR 0053).
- **The push card** (ADR 0040). It removes the proxy's start from the environment (`KILN_PROXY_CREDENTIAL`) in the same pull request, so that two ways never exist side by side. Renewing the credential replaces the proxy (card 3), which leaves the run networks of runs in flight. A proxy replaced while a run is followed is attached to its network again only when the run's command is started again (card 5). Linux accepts a packet for any of the proxy's addresses on any network it is attached to, so the push port must refuse runs by itself and cannot rely on the network it listens on.
- **The standards card.** Three of card 2's four findings were of one kind, clean-up and repeating a step on code that drives the engine. Candidate for a written standard, so that implement has it before it writes code (ADR 0015, rule 3): a function that creates or removes something on the engine leaves nothing behind when it fails, is safe to repeat (ADR 0035), and a test shows both. Also decided by the developer on 2026-11-17: commit messages and pull request titles in Kiln's repo follow Conventional Commits (`type(scope): summary`, the scope optional), from card 3 on. With squash merging the pull request's title becomes the commit on `main`, so the rule covers both. It settles the format part of "who writes commit messages and the pull request's title and text" (ADR 0020, ADR 0028); who writes them stays open. It belongs with the written standards once they exist, and a format a tool can check is a check, not review (ADR 0015, rule 4).
- **The MVP.** Kiln's layer needs a few things from a toolchain image, namely `curl`, `sha256sum`, `useradd`, `sh` and a free uid 1000. The save needs `git`, `find` and `chmod` from it as well (card 4).
- **The MVP card that rebuilds placing and collecting for Kubernetes** (ADR 0038). The developer asked on 2026-11-17 for a container that holds the instance's copy of the repo in a volume, so that nothing of a working tree touches the host's disk. For the POC the save's unpacking moved into a throwaway container instead (card 4). A volume that holds the copy is worth weighing at the MVP, with where saved and unpublished work is kept safe and how that container reaches the Git host.
- **The first UI card.** Modern Web Guidance, skills for coding agents on current web platform practice (Apache-2.0, stewarded by browser vendors and MDN), is worth trying. Runs are sealed, so it has to be in the repo or the run image, as part of the repo's Claude Code configuration, which is a protected place.
- **The visual design session.** Candidates for a short written standard for the UI: answer within about 400 ms, fewer choices, larger targets, familiar patterns, and less animation for what is used all day.
- **The card in which the core starts runs itself (the tick).** Two starts of the same `kiln run` command for the same run at the same time both collect into `<runs>/<id>.partial`, and each first removes what is there. One can delete the other's half-written files; at worst a record without the run's documents is written, and the container is then removed. The branch stays safe, since the guarded `update-ref` gives the same commit either way. The spec's table and ADR 0035 cover a second start only after the first has ended. Accepted by the developer on 2026-11-17 for runs started by hand (card 5); the card that has the core start runs settles it, for example with a lock in `internal/run`.
- **The API card.** A `Create` that is repeated after a kill writes a second card, because the caller cannot tell whether the first was written (card 6). The card settles how a repeat is recognised, for example with an identity for each request. It also adds the instance's data directory, which `store.Open` leaves to its caller (ADR 0044).
- **When Kiln builds its own cards.** A sealed implement run cannot add a Go module, because it has no network and the toolchain image carries only the modules of `go.mod` as it was built (card 6, ADR 0057). How a card whose spec needs a new module gets it is open.
- **The card that shows a run to the developer.** A `kiln run` that is started again on a run that has already ended collects, saves, records and removes without printing a line. It should say what it did: the saved commit and branch, or "no change", and where the record is (card 5).
- **The launcher card.** Unexplained, from the first real run on 2026-11-17 (card 5): on the developer's machine the freshly built `kiln` program was killed twice within a second of starting, and ran normally a few minutes later. Its signature was valid, the antivirus reported nothing, and writing a program over an existing one did not reproduce it. If it happens again with the launcher's builds (ADR 0036, ADR 0037), this card has to find the cause.
- **The stage cards.** A target repo's settings may change the effort, through `CLAUDE_CODE_EFFORT_LEVEL`, or the model, and a run's output shows only the model (card 5, ADR 0030). Whether a repo's project settings can set either is unclear; Kiln's repo has no `.claude/settings.json`.
- **The review card.** A run has no `.git` and no diff base; what a reviewing run needs of either is open. A run can also make its save fail every time, as the note on the work repo below says.
- **The work repo.** Submodules are refused (card 5), and attributes that rewrite content on `add` are applied by the save. A run can make its save fail every time: Git refuses paths such as `.GIT/x`, `git~1/x` or `.git /x`, and a symlinked `.gitmodules`, so `add -A` in the save container exits with an error on every repeat. Nothing is lost, because the run's container stays, but that run's work cannot be saved. The save's error also carries 20 raw lines of the save's output, so file names a run chose reach the terminal (card 4's review).
- **Things to read before writing Kiln's own, saved by the developer on 2026-11-17.** None is installed; a sealed run can only use what is in the repo's Claude Code configuration or the run image, pinned, with a dependency entry (ADR 0025, ADR 0051).
  - **The standards card and the visual design session:** the `learn-taste` skill (github.com/emilkowalski/skills, read at commit 64eb3de) turns a developer's design corrections into written rules. Worth borrowing: every rule traces to something the developer said and carries its reason; a rule a tool can check becomes a check (as ADR 0015, rule 4); a rule is written at the narrowest level that prevents the mistake on the next component, for an agent that was not there; it proposes and stops. It reads a conversation, which a headless run does not have; Kiln's corrections are rejected specs, review findings and interventions. `claude-md-management` in Anthropic's plugin directory (github.com/anthropics/claude-plugins-official) does a similar job for `CLAUDE.md`.
  - **The review-loop card:** the `code-review` plugin in the same directory reviews with several agents and filters findings by a confidence score. Read it before writing Kiln's review instruction (ADR 0056), for the filter, and weigh it against the cost of a review.
  - **The first UI card:** `frontend-design` from the same directory, next to Modern Web Guidance.
  - **When the code has grown:** `gopls-lsp`, which gives an agent Go's language server; it needs `gopls` in the toolchain image.
- **The CLAUDE.md card.** The check command comes first. A sentence that tells the agent it owns the codebase is an experiment to measure against send-backs, not a default.
