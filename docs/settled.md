# Settled by cards

What cards have settled under a decision, by the decision's number. A card adds its lines here, in the pull request that settles them, and never changes a file in `docs/adr/`. The decisions themselves change only by the developer (ADR 0058).

A line says what was settled and ends with the date in brackets, for example (2026-11-20). It names no card: the pull request that added a line is found with `git blame`. The lines already there stay as they are, except that a line whose "until" or "yet" a later change ends is replaced in that change's pull request. The spec that a line comes from is the text of that card's pull request.

## ADR 0005: Kiln's work ends at "ready to merge"; merging belongs to the target repo's Git host

- Where everything the Git host requires has already passed, the Git host refuses to switch on automatic merge, and Kiln asks the Git host to merge instead (ADR 0049). The Git host's rules decide in both cases; Kiln never merges past them.

## ADR 0006: Guardrails for automatic merging

- Checks now run on the Git host's own runners, not on a runner on the developer's machine (ADR 0049).
- The developer's approval of a protected path is given on the Git host. It is an intervention (ADR 0042), which the core records when it sees the approval there.
- The board's count of interventions leaves out the developer's approval of a protected path on the Git host until the core sees it, and the strip's title says so (2026-11-24).
- Kiln's review instructions, with all its stage instructions, are a protected place in Kiln's repo (ADR 0056).

## ADR 0007: Kiln optimises the developer's attention first, quality second

- A card names, when it is written, at most one earlier card that it fixes, as `fixes`, a card ID, in `POST /api/cards`, or in the field "Fixes card" of the screen's new-card dialog. It is kept in `cards.fixes` and not changed afterwards. Only a card the Git host merged can be named: the store refuses, with the reason and with nothing written, a card that does not exist, a dropped card, a card that is not merged, one closed without publishing included, and the card's own ID. The fixed card gets no entry and does not change (2026-11-24).
- A merged card needed a follow-up fix when a card that was not dropped names it. The board's measures count such cards among the merged cards, each once however many cards name it, as a query over the cards when the board is read (ADR 0042, rule 1). The board's JSON carries the number as `measures.needed_fix`, and the strip's line says `needed a follow-up fix: <n> of <merged>`. A follow-up fix that the developer does not name is not counted, and the strip's title says so (2026-11-24).
- The card's page shows `Fixes card #<n>` and `Fixed by card #<m>`, each number a link to that card's page. The JSON of the board and of the card carries `fixes`, 0 for none, and the card's JSON carries `fixed_by`, a list (2026-11-24).

## ADR 0008: One planned intervention per card: approval before any code is written

- The developer approves a spec with a move on the screen: it moves the card from spec, waiting for approval, to implement, waiting for a run. The developer's moves are one table in the store (`Decide` in `internal/store`): approve, again, send back and done (card 13, 2026-11-19). Done is the move from review, waiting for approval, where a review that passed leaves the card; ready to merge comes with publishing (card 14, 2026-11-19).
- The developer's moves carry a note, at most 16 KiB, trimmed, kept as the reason of the move's entry; no column is added. A spec that waits for approval is sent back to a spec run with a note it cannot go without (`again`), a review that passed is sent back to implement the same way (`send-back`), the moves of a stage that needs you take one or none, and approve and done refuse one. The run that follows a move with a note is told it last, under `## The developer's note`, and the note wins where it differs from the spec (card 16, 2026-11-20).
- With a publish command the table has `publish`: from review, waiting for approval, to review, waiting for the Git host, with no note. It is offered again from review, needing you, only when the card is there because its publishing failed, which its last entry says, as for a drop. From the Git host the developer has `send-back` with a note and `done`, which the page calls "Close", once the card has its pull request's address; while the core publishes it, the card has no move, drop included. A review that passes shows "Publish" first, then "Send back to implement", then "Close without publishing", today's `done` (card 19, 2026-11-20).
- Approve takes an optional note, trimmed and at most 16 KiB like every note. It is kept with the spec it approves, in the column note of that spec's row in specs, written in the move's transaction; the approval's entry has no reason, so that the next run is not also told it as the developer's note. With a note, a card that has no spec is refused (409). Approving without a note is as before (2026-11-23).
- Every implement run and every review run of a card is told its approved spec's note, if it has one, under ## The developer's note on the spec, right after ## The approved spec, with a sentence that it is the developer's correction to the spec and that the note counts where the two differ; a review judges the change against the spec as the note corrects it. A spec run that revises an approved spec is told its note after ## The last spec, under ## The developer's note on the last spec. A new approved spec has its own note or none, so the old note ends with it (2026-11-23).
- The page offers a field for the note before "Approve", empty by default, and shows an approved spec's note under that spec on the card's page, the earlier specs' as well. The core reads no line of the note: the pull request's title and the model for implement come from the spec's lines (2026-11-23).
- With a publish command a review that passes is published by the rule, with no move of the developer's. The card goes from its review run to review, waiting for the Git host, and the core publishes it as after the move publish. A change that touches the workflow files stays in review, waiting for approval, with the reason that it waits for the developer's yes and the files, and "Publish" asks for the yes as before. Without a publish command a review that passes waits for approval as before (2026-11-23).

## ADR 0009: Five stages; research is a step inside spec, not a stage

- A spec run judges the card's size first (`instructions/spec.md`, "First, the card's size"). For a card that names its change exactly, or whose change is text or a few lines in known places, it reads the files concerned and writes the spec, with no prototype, no survey of options the card decided, and no web page unless the card depends on something outside the repo the run does not know. On any card, it prototypes only what reading the code cannot decide, and only that part. The web stays open to every spec run (2026-11-23).

## ADR 0010: A card is one self-contained pull request; order is a hold on starting

- A spec whose size, as it states it, is over about 1,000 lines of code and tests together recommends a split into cards of about 800 lines each in its first question, names what goes into each and what the first card leaves out, and specifies only the first card (`instructions/spec.md`, "First, the card's size") (2026-11-23).
- A card names its predecessors when it is written, as `predecessors`, a list of card IDs, in `POST /api/cards`, or in the field "After cards" of the screen's new-card dialog. They are kept in the table `predecessors` and are not changed afterwards. The store refuses, with the reason and with nothing written, a card that names itself, a card that does not exist or a card that was dropped. A card named twice counts once, and a done one is accepted (2026-11-24).
- Starting a card with a predecessor that is not done queues it: backlog, waiting for room, by the developer, with the reason `waits for its predecessors to be done: #<n>, …`. On every tick, before runs start, the rule moves each queued card none of whose predecessors is still open. When every predecessor is done, the card goes to spec, waiting for a run, with `its predecessors are done: #<n>, …`, and its spec run starts from `main` as it is then. When one was dropped, the card goes to backlog, waiting for the developer, with `its predecessor #<n> was dropped; start it without it, or drop it`. A predecessor is done when it is in done and was not dropped, and a card closed without publishing counts as done (2026-11-24).
- A card names its repo when it is written: `repo` in `POST /api/cards`, one of the instance's repos by name, which may be left out when the instance has exactly one. A name the instance does not have, or none with more than one, is refused with 400 and the reason, and nothing is written. The repo is kept in `cards.repo` and not changed afterwards. A card made from a proposal is in the repo of the card it was noticed on, and a card's predecessors may be in another repo (2026-11-25).

## ADR 0011: A card ends as done or dropped, and only the developer drops it

- The developer drops a card with a move on the screen, `drop`, from every state but done, with one confirmation that names the card and an optional note. A card with a run in flight is not dropped (409) until stopping a run comes. The branch of a dropped card stays (card 16, 2026-11-20).
- The confirmation of a drop names the cards that name the dropped card as a predecessor and are not in done, and says that they will wait for the developer, to be started without it or dropped. The card's JSON carries them as `named_by` (2026-11-24).

## ADR 0012: A moving repo sends a card back to implement; a spec that cannot be built sends it back to spec

- A card that returns to implement from the Git host counts as a send-back, for a conflict as for a failed check (ADR 0054).
- A card that returns to spec has its spec session resumed, since that stage gets its own work back; after the new approval implement starts in a fresh session and the number of send-backs starts again (ADR 0053, ADR 0054). That approval is not the planned one and is the intervention counted here (ADR 0042). How a run reports that the spec cannot be built is listed in docs/open-points.md.
- Until a run can say that its spec cannot be built, the developer sends a card back to spec by hand: `to-spec`, from implement or review that needs you, to a spec run, with a note or without. That run starts fresh, not resumed: it is told the spec it replaces (`## The last spec`), the card's newest report or review (`## The last report` or `## The last review`), and the note, if any. A spec run after any note is told the spec it replaces as well (card 16, 2026-11-20).
- A card that waits for the Git host and whose change collides with `main` when it is published goes to implement, waiting for a run, by the rule, with the reason `main moved and the change no longer applies` and the files. The core merges `main` into the card's branch first, without a working tree, as one commit with the branch's tip and `main` as its parents and the merge's tree, conflict markers included in the style diff3, and moves the branch there. The implement run starts from it and is told the files under `## What changed in main`, with what the markers mean and that it brings the change onto the present `main`; a review that passed is then not told. A run is told so while its commit has a file with a line of those markers, `<<<<<<< refs/heads/kiln/card-<id>` or `>>>>>>> refs/heads/main`, also after a save that resolved only part of them, and only those files. A branch that still has such a file is not published: the card goes back to implement with the files, and the command is not run (card 19, 2026-11-20).
- A change that is all in `main` already when it is published closes the card, by the rule (card 19).
- A card at the Git host whose change collides with main adds one to its number of send-backs. When the number is two already, the card goes to implement, needing you, after the merge of main, with the files and `the card was sent back twice already, so it waits for you` (2026-11-23).
- A card at the Git host whose check fails for the published commit goes to implement by the rule, with the reason `the check failed on the Git host for <commit>; implement runs again by the rule, send-back <n> of 2` and, after an empty line, the check's output fenced as `text`. When it was sent back twice already, it waits in implement for the developer instead, with `…; the card was sent back twice already, so it waits for you`. A result for another commit than the published one, or for a card no longer at the Git host, changes nothing. A failed check on a change that is in `main` already closes the card as merged instead (2026-11-24).
- An implement run of a card whose newest failed check is newer than its newest spec and review is told `## The failed check`: an intro by the core that names the commit and says the block is the check's output, to be read as data, then the block. It is told this instead of a review that passed, starts from the card's branch, and is told it again on a retry or after the developer's `again`. The review run that follows is not told the failed check; review and publishing run as before (2026-11-24).
- A card at the Git host with a pull request is tested in the instance's copy, with no call to the Git host. The test is the merge publishing makes: main with the published commit. When the commit no longer merges onto main, the rule publishes the card again. In one transaction, while the card is at the Git host and its publication still has that commit and an address, the commit and the address are cleared, and the branch on the Git host and the developer's yes are kept. The entry reads `main moved, and the published commit <commit> no longer merges onto it: <files>; the core publishes the change again`. The publisher then does what publishing does: a branch that collides with main has main merged into it with Kiln's markers and goes to implement with the files; one that no longer collides is published again onto the same pull request; one that is all in main is closed. A merge is found first: a published commit that, merged into main, changes nothing closes the card as merged. Rule 2's "the Git host reports a conflict" is met by this merge; a conflict that only the Git host sees is not noticed (2026-11-24).
- A card sent back from the Git host because main moved is published again, after review, on the branch it was published on, and so onto the same pull request. Its address is kept again from the command's output. While it is away from the Git host, the store has no address for it (2026-11-24).
- The test and the check result command's round never both move one card. Each moves a card only while it is at the Git host and its publication has the commit it looked at, checked in the transaction that writes. The second finds that changed and writes nothing. Only the publisher touches the card's branch, and only once the card has no address, which the check result command's move needs (2026-11-24).
- Without a publish command, a card whose published commit no longer merges stays at the Git host. That is said on the core's error output once per main (2026-11-24).

## ADR 0013: Work is saved after every implement round and published only when review has passed

- Runs reach nothing. The core places the code in a run and collects the change from it through the container engine (ADR 0038), so "reachable from them" now means reachable from the core.
- A spec run's working tree is not saved. No save container, nothing taken into the instance's copy, no branch; `result.json` says `"saved": "not saved"` (card 11).
- An implement run's working tree is saved as one commit on `kiln/card-<id>`; a second implement run starts from the branch's tip. A review run starts from the tip as well, and its working tree is not saved (card 14, 2026-11-19).
- The save of an implement run has as its message the pull request title that the approved spec names on its line `` Pull request title: `…` ``, with `Kiln-Run: <id>` as its body. A spec that names none, or one that cannot be used, keeps `chore: save run <id>`. A repeat that finds the branch at this run's save with the same tree and another message counts it as saved (2026-11-20).
- Only a run that saves judges where the card's branch is, since only its save moves it. A spec run or a review run starts whatever the branch holds, so that a card sent back to spec, which keeps its branch, gets its spec run from the head of `main`, and the branch stays as it is for the implement run that follows (card 17, 2026-11-20).

## ADR 0014: Two limits on cards in progress, enforced by queueing

- Each repo has a limit of cards in progress: `limit` of the repo in the settings file, a whole number from 1, 3 when it is left out, and 3 for the one repo of a core started from its flags. A value below 1 refuses the core's start with the reason. A card counts against its repo's limit in spec, implement and review, whatever it waits for, ready to merge (review, waiting for the Git host) included. A card in the backlog or in done does not (2026-11-25).
- The developer's `start`, the screen's new card and `kiln card` take a card whose predecessors are done to spec, waiting for a run, only while its repo has room: fewer cards in progress than its limit, counting also the repo's cards that wait for room before it. Otherwise the card is queued, backlog waiting for room, with the reason `waits for room in its repo <name>, whose limit is <n> cards in progress`. A card whose predecessors are not all done is queued for them as before, and its repo's room is looked at once they are done. The count and the move are one transaction, so the limit holds also when the screen and the rule move cards at the same moment (2026-11-25).
- The rule takes every queued card on every tick, also while the instance is paused, one transaction each, in the order the cards began to wait for room. A card that waits for room starts once its repo has room, with the reason `its repo <name> has room under its limit of <n>`. A card whose predecessors are done while its repo has no room stays queued, with one entry of the rule that says it waits for room and that its predecessors are done. From then on it waits behind the cards that waited for room before it. A repo at its limit holds back no card of another repo. A card already in progress beyond a limit is not moved; new cards queue until fewer are in progress. A card that waits for room is not sent back to the developer for a dropped predecessor that it was started without (2026-11-25).
- `kiln core --runs` stays the limit of runs in flight across all repos, not a limit on cards: a card that the limit lets out of the backlog waits for a run in the order of the cards that wait for one, as before, and counts against its repo while it waits (2026-11-25).
- With more than one repo, the new-card dialog has the field Repo, with the instance's repos in the settings' order, the first preselected, each with its cards in progress and its limit. Every tile and the card's page show the card's repo's name. With one repo none of it shows. `GET /api/board` carries `limit` and `in_progress` for each entry of `repos` (2026-11-25).
- The instance has a limit of cards in progress: `limit` at the top of the settings file, beside `repos`. It is a whole number from 1, and 3 when it is left out or the core is started from its flags. A value below 1 refuses the start of `kiln core` and of `kiln card`, with the reason. A card counts against it in spec, implement and review, whatever it waits for, except ready to merge (review, waiting for the Git host), across all repos (2026-11-25).
- `start`, the screen's new card, `kiln card` and the rule take a card out of the queue only while its repo and the instance both have room. They go through the cards that wait for room in one order across all repos. A card ahead takes a place only when both its own repo and the instance have room for it. A repo at its limit holds back no card of another repo, and the instance's limit holds back the cards of every repo (2026-11-25).
- A queued card names one limit in its reason. While its repo has no room, it names the repo, with the words as before. Otherwise it names the instance: `waits for room in the instance, whose limit is <n> cards in progress that are not ready to merge`. When the limit that holds it changes, the rule writes one entry with the new reason, and the card keeps its place, its `since` unchanged. It starts with `its repo <name> has room under its limit of <n>` or `the instance has room under its limit of <n>`, by the limit it last waited for (2026-11-25).
- A card that comes back from the Git host to implement, by a failed check or the developer's send-back, counts against the instance again at once, also at its limit. The limits hold back starts, and new cards queue until fewer are in progress (2026-11-25).
- `GET /api/board` carries `instance_limit` with `limit` and `in_progress`. The screen shows one line above the columns: each repo's cards in progress of its limit, and the instance's of its limit. With one repo it shows only that repo's (2026-11-25).
- With `--runs` at least the instance's limit, as with both defaults of 3, the limit of runs never holds back a card. With fewer runs, cards wait for a run in the order of `store.Waiting` across repos, as before (2026-11-25).
- A queued card whose `since` cannot be read takes no place in the queue for room. The cards of every repo are counted as if it were not there, and no other card's start or move is refused for it. It does not start itself until its `since` is repaired (2026-11-25).

## ADR 0015: Review blocks only on the spec, a concrete failure or a written standard

- "Not written anywhere" means that remarks are no part of review's result and are shown to nobody. The full output of a review run is still kept, like any run's (ADR 0032, ADR 0038).
- Every review round starts in a fresh session; a stage that is sent back resumes its own (ADR 0053).
- The number of send-backs is a fact on the card, and a failed check on the Git host counts as one (ADR 0054).
- A review run is told the card, the approved spec and the diff, from where the card's branch left `main` to its tip, made in the instance's copy, and writes `review.md` with its verdict as the first line, `Verdict: passes` or `Verdict: goes back`. A diff over 1 MiB starts no review run, and the card needs the developer with the size. A change that goes back is sent back to implement by the rule of the next line. The next implement run is told the last review when it sent the change back (card 14, 2026-11-19).
- A review run that finishes with `Verdict: goes back` while its card's number of send-backs is below two sends the card to implement, waiting for a run, by the rule, in the transaction that ends the review run. The run's entry stays as before, at review needing you. The rule's entry follows with `the review sent the change back; implement runs again by the rule, send-back <n> of 2`, and the number goes up by one. At two or more, the rule's entry keeps the card under "needs you", saying that review sent it back a third time, or again, and the developer's moves are as before. The next implement run is told the last review as before (2026-11-23).

## ADR 0016: Run failures are handled by a few fixed rules, not by a supervising agent

- Whether a run has been retried is a fact on the card (ADR 0054).
- That the instance is paused is state of the instance, kept in the store with its own history (ADR 0055).
- A failed run is run once more by the rule, in the same stage, from where a second run of that stage starts: a spec run from the head of `main`, and an implement or review run from the card's branch. The run's entry is under "needs you" with its reason, and an entry of the rule follows in the same transaction, with the card waiting for a run, "the run failed, and the rule runs it once more; " and the run's reason. When that retry fails as well, the rule's entry keeps the card under "needs you" with both reasons. A finished run that stops under "needs you" has no retry. Finished and failed are told apart by the run's record (ADR 0043) (2026-11-24).
- A run whose result carries `api_error_status` 401 uses up no retry. The rule's entry has the card wait for a run, which the tick starts once the instance is not paused. A refusal on the retry keeps it the retry. A refused run whose result is missing is an ordinary failure (2026-11-24).
- A move of the developer's makes the card's next run a first run, with a retry of its own (2026-11-24).
- A run ended by that bound, or for its removed instruction or its unreadable `documents.tar`, is a failed run: its reason says what was wrong and what to do, the rule runs it once more, and a second failure keeps the card under "needs you" with both reasons (2026-11-24).

## ADR 0017: Every run is sealed, and credentials stay behind a proxy

- Where the proxy sits: a container of its own on the runs' network (ADR 0034).
- "Results out only through save" was too narrow for a spec or a verdict. Results leave a run only through what the core collects after it has ended (ADR 0038).
- The proxy does not hold the renewable secret. The core runs a command that yields a credential and pushes the result to the proxy (ADR 0040).
- How a network is sealed on the developer's container engine (ADR 0041).
- The checks runner is not covered by this decision; it is isolated, not sealed (ADR 0046).
- "A second runtime later without rework" was given up for one place: placing files in a run and collecting them from it is rebuilt for Kubernetes (ADR 0038).
- The proxy lets a request's body be read while its answer is passed on (`EnableFullDuplex`), so that Go's HTTP/1 server does not close the body at the answer's first write. What a run can reach or obtain does not change (card 10, 2026-11-18).
- A run with a list of hosts reaches HTTPS on port 443 of the hosts on it through a way out of its own, and the way out's address rule (item 1 of card 12's spec) is decided on the address after the name is resolved: a name with one refused answer is refused whole, and the address judged is the one connected to. An empty list is the seal as before. Only spec runs have a list, `kiln core --spec-hosts`, and a spec run may read the web (the developer's decision of 2026-11-18, ADR 0009, ADR 0059) (card 12, 2026-11-19).
- A card is published on `card/<id>-<name>`, the name from the pull request's title without its Conventional Commits type and scope: lower case, ASCII letters and digits, hyphens between, as many whole words as fit in 50 characters. The name is kept with the card's publication at its first publishing and given on every later one, so that a title that changes opens no second pull request. The core hands the name to the publish command, which pushes; the save stays on `kiln/card-<id>` in the instance's copy (card 19, 2026-11-20).
- The proxy starts with no credential and takes one only from a push, never from its environment: `KILN_PROXY_CREDENTIAL` and `kiln proxy` are gone. Until the first push a run's request gets a 503 of the proxy's own that names the cause, and nothing is forwarded. The push has no address: the seal runs `docker exec --interactive <proxy> /proxy push` with the credential on standard input, and that program hands it to the running proxy over the Unix socket `/run/kiln/push.sock`, on a tmpfs of the proxy's user, 65532, with the mode 0700. It is a path in the container's own mounts and not an abstract socket, because an abstract socket belongs to the network namespace, which another container can join, and has no permissions. The credential is never an argument, in an environment, in a file on the developer's machine, printed or in the store; the proxy takes printable ASCII of up to 64 KiB (2026-11-23).
- A spec run's list of hosts is its card's repo's. With the flags it is `--spec-hosts`, as before (2026-11-25).

## ADR 0018: The POC runs on the developer's machine; Kubernetes is the second runtime

- A run is not quite "a pod in all but name": placing files in a run and collecting them from it uses the container engine and is rebuilt for Kubernetes at the MVP (ADR 0038).
- Kiln no longer runs from a checkout. Each version is a program built in a sealed container, with the previous one kept beside it (ADR 0036, ADR 0037).

## ADR 0019: Kiln updates itself after a merge to its own repo

- Which process an update restarts, and why runs do not notice (ADR 0034, ADR 0035).
- Who judges a new version and undoes a failed update, and what happens to the store when it is undone (ADR 0036).
- Where the new version is built (ADR 0037).
- Kiln no longer runs from a checkout. Each version is a program built in a sealed container, with the previous one kept beside it (ADR 0036, ADR 0037).
- That automatic merging is off after a failed update is state of the instance (ADR 0055).
- The board's header names the running version: the commit set at build by `-X main.version`, or "built by hand" (2026-11-23).
- A core started by `scripts/kiln-up` from a source without uncommitted changes is built with `-X main.version=<the source's head>`, and updates itself as any other. From a source with uncommitted changes it is built without a version, which the script says once (2026-11-24).
- An update follows any change to `main` of Kiln's own repo, not only the instance's cards (the developer's answer of 2026-11-23). An update is due when `main`'s head is not the running version and the running version is an ancestor of it. A core built by hand updates once one of the instance's cards has merged since it started, which is kept in memory only. Kiln's own repo is the one whose `go.mod` at `main`'s head names the module path of the core's build information. A core without a launcher never updates, and says so once (2026-11-23).
- The update builds the images too, each under the new version's tag `<name>:<first 12 hex digits>` and never under the plain name. It builds `kiln-toolchain` on every update, from the engine's cache when nothing changed (the developer's answer of 2026-11-23), and the program in `kiln-toolchain:<tag>`. When the images' files changed between the running version and `main`'s head (`images/`, `cmd/proxy/`, `cmd/wayout/`, `go.mod`, `go.sum`), and always for a core built by hand, which cannot tell, it builds `kiln-proxy`, `kiln-wayout` and `kiln-run` as well, in the README's order, after the toolchain and before the program. A diff that fails counts as changed. A failed image build is a failed build: it is printed, and tried again when `main` moves (2026-11-23).
- After a failed update the previous core turns automatic merging off before it opens its screen. The state is the columns `merging_off`, the reason, and `failed_update`, the commit, of `instance`, in store version 11, written with an entry of cause `rule` in one transaction. The reason names the failed commit, the launcher's reason and the version the core went back to. A second failed update while merging is off replaces both (2026-11-23).
- While automatic merging is off, the rule publishes no card: a review that passes waits in review for the developer, with the reason "automatic merging is off after a failed update". "Publish" works as before, and the publish command is not told (the developer's answer of 2026-11-23).
- While it is off, the core does not update to `failed_update`, which it reads from the store on every look, so also after a restart. Every other head that is due is updated to, and merging stays off (2026-11-23).
- The developer turns it on with "Turn automatic merging on" on the screen, `POST /api/instance/decide` with `{"action": "merging-on"}`. This writes an entry of cause `developer`, clears `failed_update`, and so tries the update again with `main` still at that commit. With merging on it is refused with 409 (2026-11-23).
- Only a card of Kiln's own repo that merges counts for a core built by hand: a merge of a card of another repo does not update it. The update reads only Kiln's own `main` (2026-11-25).
- While automatic merging is off after a failed update, the rule publishes no card of any repo (2026-11-25).

## ADR 0020: Stage runs use Claude Code's headless command line, and nothing calls a model outside a run

- Which part of a run's image is Kiln's, and so where the pinned Claude Code version lives (ADR 0039).
- How code and instructions get into a run and results out of it (ADR 0038).
- A run's command line is `sh -c 'exec claude "$@" < /kiln/instruction.md' sh -p --output-format stream-json --verbose --permission-mode bypassPermissions --model <id> --effort <level>`, without `--bare`, so that the repo's `CLAUDE.md` reaches the prompt. The instruction comes on standard input.
- A run with a list gets `HTTPS_PROXY` and `https_proxy`, which name its way out, and `NO_PROXY` and `no_proxy`, which name the proxy; `HTTP_PROXY` is not set. Claude Code 2.1.326 takes the first of these variables for all its traffic, the model's included, so without `NO_PROXY` its requests to `ANTHROPIC_BASE_URL` would go to the way out, with the placeholder key. The variables are a convenience: a repo's settings can change them and so break a run, never widen what it reaches, since the network decides (ADR 0059) (card 12, 2026-11-19).
- Nothing outside a run writes the pull request's title or text. The title is the approved spec's `` Pull request title: `…` ``, or the card's first line cut to 72 characters; the text is the newest `/kiln/out/pull-request.md` that an implement run wrote, kept as a document of the kind `pull-request` beside its report, or the card's text when it has none (card 19, 2026-11-20).

## ADR 0021: A spec is one short document of Kiln's own, borrowed once from Spec Kit

- A spec run is told `instructions/spec.md` and the card's text, and writes one file, `/kiln/out/spec.md`, of at most 256 KiB. The core reads no line of it (card 11).
- The core reads one line of an approved spec: the first `` Pull request title: `…` `` before its first `## ` heading. The title is at most 256 bytes and has no backtick, control character or bidirectional control character (2026-11-20).

## ADR 0022: The UI shows what needs the developer first; the board is second

- The first screen shows everything that waits for the developer: specs to approve, drops to confirm, and cards in the state "needs you". The term itself keeps its narrower meaning from CONTEXT.md, a card that has stopped outside the planned approval.
- The strip shows of each card its headline: the first sentence of its first line, cut to at most 90 characters with an ellipsis, on one line. The board's JSON carries it as `headline`, beside `title`. The tiles, the card's page and the drop dialog keep the whole first line (2026-11-20).
- The board shows each card's cost on its tile, the total with the stages in the tile's title, and the card's page shows it with the stages on one line. The figure is Claude Code's estimate, summed from what each ended run of the card added, in dollars with two decimals. `+?` follows a part that has a run of unknown cost, and `?` stands for a part with nothing known. A run in flight counts nothing yet. The board's JSON carries it as `cost`, with `text` and `label` (2026-11-24).
- The strip's "Needs you" also lists a backlog card that waits for the developer because a predecessor was dropped, with its reason (2026-11-24).
- The board shows its measures in one small strip under the strip of what needs you: the cards merged, the interventions per merged card (their total over the merged cards, divided by their number, `–` with none) and the cards dropped, over the whole history. The board's JSON carries them as `measures`, with `merged`, `interventions`, `per_merged` and `dropped`, and the line as `text`. A tile shows its card's interventions when there are any, and the card's page always shows them. The JSON of the board and of the card carries the number as `interventions` (2026-11-24).
- A tile's bottom line wraps onto another line when its parts do not fit, each part whole on its line; the documents stay at the right end of the last line, cut with an ellipsis only when they alone are wider than the tile (2026-11-25).

## ADR 0023: Kiln's core is written in Go, its UI in Svelte

- The first screen is one embedded page, `internal/web/index.html`, with its CSS and JavaScript inside, and no build step, no dependency and nothing loaded from the network. A Svelte client replaces it when the screen outgrows one file (card 13, 2026-11-19).
- For work on the screen, `kiln core --page <file>` reads the page from that file on every request instead of the embedded one. Its Content-Security-Policy is computed from the file's own script and style, as the embedded page's is, so that the page runs as it will once embedded. A file that cannot be read, or that lacks a script or a style, is refused at start, and also refused without a screen (`--listen` empty). At a request it gives 500, never the embedded page (2026-11-20).

## ADR 0025: Kiln's settings for a repo live in the instance; the repo's own Claude Code configuration is picked up from the repo

- Protected paths and the required checks are not settings in the instance. For a repo that merges automatically the Git host enforces both, from the code owner file in the repo and from its own rules (ADR 0047, ADR 0049), and the checks are a command in the repo (ADR 0045). Each still has one place. The instance holds what a Git host cannot: whether automatic merging is used, the limit, branch naming and the toolchain image (ADR 0039).
- The list of hosts of a stage is in the instance: a spec run's is `spec_hosts` of its repo in the settings file, or `kiln core --spec-hosts` for a core started from its flags. `kiln run` has no list, so a run started by hand is sealed as before (ADR 0059) (card 12, 2026-11-19; 2026-11-25).
- Kiln's own repo has a `CLAUDE.md` with its rules for every run and every session in it: the docs to read, Conventional Commits for commit messages and pull request titles, and that the repo is public. A run reads it from what is merged (rule 2). It is a protected place (ADR 0047) (card 11).
- The core holds its repos as a list, each with a name of ASCII letters, digits and `-`, at most 40 characters, unique, the path of its bare copy, its publish command, its check result command and its spec runs' list of hosts, and exactly one marked as Kiln's own. The list is read from the settings file of `--settings`, or is one repo, `kiln`, Kiln's own, made from `--repo`, `--publish-command`, `--check-result-command` and `--spec-hosts`; a core given `--settings` with any of those four is refused. A core of more than one repo starts. Each card's runs, publishing, check result command and tests at the Git host use its card's repo (2026-11-25).
- The settings file is JSON, read with Go's `encoding/json`: one object whose member `repos` is a list of objects with `name`, `copy`, `own`, `publish_command`, `check_result_command` and `spec_hosts`, the last three optional. A member it does not know is refused, so that a misspelt one is not a setting silently left out; the limits come as members when their cards read them. `copy` is an absolute path. A file over 1 MiB, one with anything after the object, and one `settings.Check` refuses are refused with the reason, and the core does not start. Every core reads the file at its start, the new core of an update too; a change while a core runs counts from the next start (2026-11-25).
- A repo that is not in the settings while it has cards that are not done or dropped refuses the core's start, naming the repo and the cards; a core started from its flags has the one repo `kiln`. A done or dropped card of such a repo keeps the repo's name, its change on the card's page says that the repo is not in the settings, and no card is made from a proposal on it (2026-11-25).
- `kiln card` writes its card in the repo of `--repo`, which must be one of the repos of the settings file of `--settings`, or `kiln` without a file; without `--repo`, in the one repo there is. With more than one and no `--repo` it writes nothing and says why (2026-11-25).
- `scripts/kiln-up` gives `KILN_SETTINGS`, when it is set, as `--settings`, and then none of `--repo`, `--spec-hosts`, `--publish-command` and `--check-result-command`; it then neither makes nor fetches the copy of `KILN_REPO`, and refuses a program without `--settings` (2026-11-25).
- `scripts/kiln-up` makes a relative `KILN_SETTINGS` absolute once, from the directory it is run in, with its directories' symlinks resolved, and says the path it gives (2026-11-25).
- The board's header shows Kiln's own copy when the instance has one repo, and every repo's name and copy, in the settings' order, when it has more. `GET /api/board` carries them as `repos`, beside `repo` (2026-11-25).
- Kiln's `CLAUDE.md` was rewritten by the same lens as the stage instructions, with its three rules kept (2026-11-25).
- The settings file's repos take `work_item`, `"required"` or left out. Any other value is refused with the reason, and the core does not start. A core started from its flags requires none (2026-11-25).

## ADR 0026: Kiln's repo lives in the developer's personal space on their company's GitHub; checks run on the developer's machine

- How the checks are defined (ADR 0045).
- How the runner is protected: isolated like a hosted runner, not sealed like a run (ADR 0046).
- Where tests run that need the container engine, which the runner does not have (ADR 0048).
- Kiln cannot act as an app on a personal repo on this Git host, so the fallback this decision names was taken: a public repo on github.com under the developer's personal account, with checks on the Git host's own runners (ADR 0049). GitHub as the first Git host, Kiln building no checker, and Kiln acting under its own identity all stand.
- Of this decision's cost rules, two stand: Kiln's repo causes no billable usage, and there are no hosted background jobs. The rules about the developer's own runner and its caches ended with that runner (ADR 0049). What may be stored on the Git host, and how CPU time per check run is recorded there (ADR 0031), is settled by the card that needs it.
- What may be stored on the Git host: Actions caches of Kiln's repo, within the default limit of 10 GB, which costs nothing. The limit is not raised, and over it the Git host evicts the entries accessed longest ago. Only the workflow `cache`, on a push to `main`, saves; it runs none of the repo's code but the protected script, workflows and Dockerfile, and compiles the rest without running it. The check on pull requests restores and has a read-only cache token (`cache-mode: read`) (2026-11-20).

## ADR 0027: Azure DevOps is supported as a thin slice for the work repo, built to be deleted

- A card holds at most one work item number, a whole number from 1 to 2147483647, in `cards.work_item`, NULL for none. It is given when the card is written (`"work_item"` in `POST /api/cards`, the field "Work item" of the new-card dialog), or with the approval of its spec (`"work_item"` beside the note). A later approval replaces it, and an approval without one leaves it. Publish gives one to a card that has none, and refuses a different one. Nothing else writes it. A bad value is refused with 400 and the reason, and nothing is written (2026-11-25).
- A repo whose settings have `"work_item": "required"` publishes no card without a number. A review that passes leaves such a card in review, waiting for approval, by the rule, with the reason `the repo <name> needs a work item number before publishing; give it with the approval or when you publish`. "Publish" then shows a field for the number, and publish without one is refused with 400 and that reason. The publisher refuses such a card the same way, before it writes anything, as a failed publishing. Giving the number with "Publish" is an intervention, as the move publish always was (2026-11-25).
- Kiln links nothing itself: the publish command gets the number as `KILN_WORK_ITEM`, set only when the card has one and taken out of the core's own environment otherwise, and links it. Kiln does not create, read or check work items, and shows the number as `#<n>` on the tile and the card's page, linked to nothing (2026-11-25).
- The core learns of a merge on Azure DevOps as on GitHub, from the copy's `main` with no call to the Git host. A squash commit with a message of the Git host's own is found, since only trees are compared (tried with git 2.47.3: squash, no-fast-forward and semi-linear merges) (2026-11-25).

## ADR 0029: Every run has three ceilings, and a run that hits one is not retried

- Each run's cost is kept in the store in the transaction that ends it: the result's `total_cost_usd` and `session_id`, in the columns `cost` and `session` of `runs`. A run with no result, and an `error_during_execution` result with a cost of 0, which Claude Code may zero after a crash, have no cost. Such a cost is shown as unknown, never as 0 (2026-11-24).
- `--max-budget-usd` counts only a run's own spend, not the totals a resumed session restores (Claude Code's documentation and a try with 2.1.326, both 2026-11-24), so the budget ceiling needs no allowance for a resumed run (2026-11-24).

## ADR 0030: Opus for spec and review, a model proposed per card for implement, Fable only as an advisor

- That a send-back happened is read from the number of send-backs on the card (ADR 0054). A session that is resumed after a send-back continues on the stronger model (ADR 0053).
- The core compares the model that a run's first event, `system/init`, names with the one it gave. A run on another model is stopped, saved and recorded with the model seen, and the command exits non-zero. Claude Code 2.1.326's output does not show the effort, so the effort recorded is the one given.
- The model of each stage is a flag of the core, `--model` for spec and `--implement-model` and `--review-model`, which default to `--model`, and the effort is fixed per stage: spec `high`, implement `medium`, review `high`. `kiln core --effort` is gone; `kiln run` by hand keeps its `--effort` (card 14, 2026-11-19).
- An implement run starts on the model the approved spec names on its line `Model for implement: <identifier>`, with or without backticks, when the identifier is one of `claude-opus-5-5`, `claude-sonnet-5-5` and `claude-haiku-5-5`, the three `instructions/spec.md` allows. The line is read like the title's line: in the head before the first `## `, a list item allowed, the first such line deciding. Otherwise the run uses `--implement-model`, which is now only that fallback. The model is chosen when the run's row is built and kept in it, so a run in flight keeps its model across a restarted core. Spec and review runs keep their flags (2026-11-23).
- An implement run of a card whose number of send-backs is above zero starts on `claude-opus-5-5`, whatever its spec names, also after main moved. Otherwise it starts on the spec's model, as above. The model is chosen when the run's row is built (2026-11-23).
- The board's header says `implement on the model its spec names, else <--implement-model>, and on claude-opus-5-5 after a send-back` (2026-11-23).

## ADR 0031: Checks on Kiln's own repo stay fast by structure, not by a stopwatch

- The checks are one command in the repo, and these rules live in it (ADR 0045).
- The checks now run on the Git host's own runners and not on the developer's machine (ADR 0049). The rules stand, since those machines vary in speed as well.
- On the Git host, a pull request whose merge commit changes, against its first parent and with renames counted at both names, only files under `docs/` or the files `README.md`, `CONTEXT.md` and `CLAUDE.md` runs no engine tests. Any other path, an empty diff or a diff that fails runs them all. The rule lives only in `.github/workflows/check.yml`, so a change to it needs the developer's yes before the push (ADR 0060) and the code owner's approval at the merge. The engine jobs that skip still report, and the required check still waits for them (2026-11-25).
- Each test runs once per check. The engine part runs only the tests that read `KILN_ENGINE_TESTS`, as the check program finds them, and the unit tests run only in the check, in the toolchain image (2026-11-25).

## ADR 0032: Kiln keeps its data in one embedded database file

- The file is SQLite, and `sqlite3 <file> .dump` is the readable export of rule 2 (ADR 0057).
- The schema is version 2: besides cards and their entries, an `instance` table with one row, the instance's identity of eight hex digits, and a `runs` table with one row per run, with a run's ending empty while it is in flight. A run's row is kept for good, so that the measures can count it (ADR 0029, ADR 0030); the files of its record stay until its card is done or dropped (ADR 0053), and are removed by the card that first ends a card.
- The schema is version 3, with `specs`, one row per spec, written in the transaction that ends its run (card 11).
- The schema is version 5, after card 13's version 4 with the time a run started: `specs` holds every run's document, one row per run, with a column `kind`, `spec`, `report` or `review`; the rows that were there are specs (card 14, 2026-11-19).
- The schema is version 7: `specs` is keyed by a document's run and kind, since an implement run keeps two, its report and the pull request's text, and the rows keep their order; `publishes` holds a card's publication, one row per card the developer has published: the commit of the branch whose workflow files the developer said yes to, once published the commit and the pull request's address, and the branch on the Git host, kept from the first publishing (card 19, 2026-11-20).
- The schema is version 8: specs has a column note, the developer's note on approving that spec, NULL on every other row (2026-11-23).
- The schema is version 12. `runs` has `stage`, the stage its card waited in for it, filled for the runs that were there from the history; `cost` and `session`, from its result; and `unread`, 1 for an ended run whose `result.json` no core has read yet. `unread` was set for the runs that had ended before the migration (2026-11-24).
- The schema is version 13: `predecessors`, one row per card and predecessor, written in the transaction that writes the card (2026-11-24).
- The schema is version 14: `proposals`, one row per proposal a review run wrote, with the card it was noticed on, the run, its place in the file, its title and text as written, the card made from it and the note it was dismissed with, NULL until then; and `entries.proposal`, the proposal an entry is about, NULL on every other entry (2026-11-24).
- The schema is version 15: `cards.fixes`, the merged card a card fixes, NULL on every other card and on the cards that were there (2026-11-24).
- The schema is version 16: `cards.repo`, the name of the card's repo. Every card that was there is in `kiln`, the one repo of an instance started from its flags (2026-11-25).
- The schema is version 17: `cards.work_item`, the card's work item number, NULL on every card without one and on the cards that were there (2026-11-25).

## ADR 0033: A problem review notices outside a card's change is proposed to the developer, not acted on

- A review run writes its proposals to `/kiln/out/proposals.md`, each starting with a line `Proposal: <title>`, its text running to the next such line. A review with none writes no file. The core reads the line in any case, after list, quote, heading and bold marks, and with a number after the word (2026-11-24).
- A proposal the core cannot read the shape of is kept as one proposal, with its text as written and an empty title. Such a proposal is text before the first title line that is more than blank lines and headings, or a file with no title line. A `Proposal: none` with no text is no proposal (2026-11-24).
- A finished review run's proposals are written in the transaction that ends the run, so a run read again keeps them once. A `proposals.md` that cannot be taken (over 256 KiB, not a file, a damaged archive) is said in the run's reason and keeps nothing, and the run stays finished (2026-11-24).
- The first screen shows the open proposals in a part of their own under "Needs you", which does not count them: each with its title, the card it was noticed on and its text on demand. "Make a card" writes a backlog card, not started, from the title and the text, and the proposal keeps the card's ID. "Dismiss" takes an optional note. A proposal acted on is no longer open, and a second move on it is refused with 409 (2026-11-24).
- The board's measures count the proposals made, accepted and dismissed, over the whole history, from the `proposals` rows. The board's JSON carries them as `measures.proposals`, with `made`, `accepted` and `dismissed` (2026-11-24).
- A card made from a proposal is not a follow-up fix: "Make a card" names no fixed card, and the card the proposal was noticed on is not counted as needing a fix for it (2026-11-24).

## ADR 0034: Kiln is a core on the developer's machine, a proxy in a container, and one detached container per run

> Since ADR 0059 a run with a list of hosts has a way out, a fourth kind of process. The lines below still hold.

- The core is not started from a checkout but from a program built in a sealed container (ADR 0036, ADR 0037).
- The core does not depend on the directory it was started in: it makes its paths absolute at its start, runs git in the instance's copy of the repo and every other command, through the seal, in the data directory (card 16, 2026-11-20).
- `--page` is made absolute at start, like `--data` and `--repo` (2026-11-20).
- `kiln core` refuses a `--settings` that is not an absolute path, with exit status 2 and before it reads the file: every core a launcher starts reads the file again from the directory the launcher was started in, which may be gone by then. The launcher still parses none of the core's flags (2026-11-25).
- The core owns the proxy. `kiln core` reads `KILN_CLAUDE_UPSTREAM` and `KILN_CLAUDE_CREDENTIAL_COMMAND` and does not start without them. At its start it keeps a proxy of Kiln's that runs with the image of its name as that is then and with the same upstream, since replacing it cuts the runs in flight from it, and starts or replaces any other; a proxy it cannot keep ends the core. It pushes a credential before the first tick. `kiln card` needs nothing of it, and `kiln run` by hand uses the proxy that a core keeps: without a core's push its requests get the proxy's 503 (2026-11-23).
- The proxy is kept, and the first credential pushed, after the core's report; a core whose launcher is gone ends as on SIGTERM (2026-11-23).
- An update whose proxy image changed replaces the proxy at the new core's start, after the promotion, since `KeepProxy` keeps only a proxy that runs with the image of its name as it is then. A run in flight has no proxy on its network from the old proxy's removal until its follower attaches the new one in the first tick, a few seconds, and a request in progress is cut. Headless Claude Code rode out outages of 5 to 120 seconds when this was measured on 2026-11-14. A run in flight keeps the run image and the way out it was created with (2026-11-23).
- `scripts/kiln-up` takes the upstream and the credential command from `KILN_CLAUDE_UPSTREAM` and `KILN_CLAUDE_CREDENTIAL_COMMAND`, and each one that is unset from `~/.claude/settings.json` (`.env.ANTHROPIC_BASE_URL`, `.apiKeyHelper`). It exports them and prints neither. It refuses to start while `CLAUDECODE` is set (2026-11-24).

## ADR 0035: The core keeps nothing in memory that matters; it reconciles the store, the container engine and the Git host

- A run's work is saved, then the run is recorded, and only then is its container removed (rule 3). The same command started again is a repeat of the run and not a retry: each step looks at what is there and goes on from it, so a repeat uses up nothing of ADR 0016.
- One core at a time holds a data directory: `kiln core` takes `flock` on `<dir>/lock` for the life of its process, and a second core, or `kiln card`, is refused. The kernel drops the lock with the process, also when a child such as `docker logs` lives on. The store's unique index refuses a second run in flight per card as well, since a lock alone does not guarantee one holder (card 8, 2026-11-18).
- The engine's things are known as an instance's by the label `kiln.instance` with the instance's eight hex digits, beside `kiln.run`, on a run's network and container (rule 2). Every tick sweeps first: what carries both labels and is not in flight in the store is removed (rule 4). Nothing without both labels is touched, and `kiln run` by hand sets no instance, so no core lists what it made (card 8).
- A run is written to the store between placing its container and starting it, so that a kill before leaves a container that never started, which the sweep removes, and a kill after leaves a run whose files are placed again into the container that is there, which is then started once.
- From the moment a run is in the store until its result is recorded, nothing in the core removes its container or network, and its container is never created again. A step that fails, an interrupt or a kill in between changes nothing, and the next tick goes on from what is there. Only the engine losing a container makes a run gone: one with no container and nothing recorded is failed (rule 4) (by the developer's decision of 2026-11-19, after card 8's second review).
- At a run's end the work is saved, then `result.json` is written, then the store, and only then are the container and network removed (rule 3) (card 8).
- A run's ID is `<instance>-<card>-<number of the card's runs + 1>`. It is the same on every tick until the run is in the store, and the engine allows one container per name, so a wait gets one run (card 8).
- A run with a list has a way out, the container `kiln-wayout-<id>`, with the labels `kiln.run=<id>`, `kiln.wayout=1` and, with an instance, `kiln.instance`. `RemoveRun` removes the save container, then the run's container, then the way out, then the network, each skipped when it is missing. `ListRuns` lists a way out of the instance as well, so that one left by a kill between two removals is swept. A way out without `kiln.run=<id>` is refused and left as it is (ADR 0059) (card 12, 2026-11-19).
- From the moment a run is in the store until its result is recorded, nothing in the core removes its way out or creates it again, as for its container and network. A stopped way out is started again before its run starts, and when a running run is carried again. A way out that is gone before its run has started leaves the run in flight, said on every tick; one that is gone while its run runs is said in the core's output, and the run goes on without the web (card 12, 2026-11-19).
- The tick does not wait for a run. It decides for every card that waits what it did before: start a run, carry one in flight on, or end one as gone. A follower beside the tick then carries the run to its end, records it and removes it, so that the next tick comes after the interval whatever the runs do. A card has one follower at a time, and a tick leaves a card whose run is followed alone. The core keeps the followers' runs in memory only as a guard: the tick counts them, and the sweep leaves them alone, since a run is placed before it is in the store. A core started again has none, and the store and the engine say what is in flight (card 17, 2026-11-20).
- `kiln core --runs <n>`, 3 by default, from 1 to 8: a run is started only while fewer than n runs are in flight, counted as the runs in flight in the store and the followers' runs that are not in it yet. `AddRun` refuses a run beyond n in its own transaction as well. The upper bound is there because every run takes a network, and a container engine has about thirty address ranges for networks by default, which other work shares. The runs in flight that a core finds at its start are all picked up, also when they are more than n, and no new run starts until fewer than n are in flight (card 17).
- The cards that wait are taken furthest along first, review, then implement, then spec, so that cards reach the developer before new ones begin; in a stage, the card that has waited longest first (card 17).
- Ctrl-C ends the following of every run and the tick; the core returns when every follower has, and the runs go on in their containers. One run's failure or error touches only its card, and is printed with the card's ID (card 17).
- The copy's `main` follows its origin: with a remote `origin` the core fetches `+refs/heads/main:refs/heads/main` before it starts a run and before it publishes, at most once in 30 seconds and that often while a card waits for the Git host. A fetch runs beside the tick, which waits for it at most 5 seconds and then starts runs from the `main` that is there, so that a slow origin holds no run back; a publisher waits for it to its end. It runs in a session of its own with no terminal, git never prompts, ssh runs with `-o BatchMode=yes` after the developer's `GIT_SSH_COMMAND`, the copy's `core.sshCommand` or `ssh`, and at the limit of 30 seconds the whole session is killed. A fetch that fails is printed once per text, and the `main` that is there is used; a copy without `origin` is used as it is (card 19, 2026-11-20).
- A card that waits for the Git host without a pull request is published by a publisher beside the tick, like a run's follower and counted in no limit, one per card. Its commit is made the same from the same branch and `main`, so a publisher a kill stopped is started again by the next core and publishes the same commit once more; the address is kept, with an entry of the rule, only after the command has printed it. Ctrl-C ends the command with the core. An error of the publishing itself, not of the command, moves the card to review, needing you, with the reason, as a failed command does, so that no card is left without a move and nothing is tried again on every tick. After every fetch a card with a pull request whose published commit, merged into `main`, changes nothing is done, by the Git host, with the reason `merged`; a pull request closed without a merge is not noticed (card 19).
- Every core starts in one order: store, screen without actions, the comparison, the report, and only then the proxy, the credential and the ticks. A core does not know whether it is on probation (2026-11-23).
- Under a launcher, `main` is fetched at most once in 30 seconds on every tick, also when no run may start and no card waits for the Git host, so that an update is seen. The tick does not wait for that fetch (2026-11-23).
- After the store is opened and before the screen, the core reads the cost of every unread run from `<data>/runs/<id>/result.json`, once, in one transaction. A run without a record, or with one that cannot be read, keeps an unknown cost and is read no more. A failure is printed and the core goes on; the runs are read at the next start (2026-11-24).
- Of the check result command, the core keeps only when it last ran it for a card's commit, whether it runs, and the text it said last, in memory. A core started again runs it at once (2026-11-24).
- The rule that starts a queued card runs on every tick, also while the instance is paused. Each card is one transaction, and a card that still waits writes nothing, so a repeat or a core started again changes nothing twice (2026-11-24).
- A queued card that the rule cannot take, because its `since` cannot be read or its transaction fails, is printed on the core's error output with its ID, one line per card, as `kiln core: queued cards: card <n>: <error>`. The rule goes on with the next card in the queue. Nothing of that card is written, and the next tick tries it again (2026-11-25).
- A run in flight with no record whose container is created, paused, restarting, being removed or dead holds its place for ever by itself. The core notes, in memory, when it first sees a run in one of those states, and the rule ends the run as failed once the same core has seen it in the same state for 5 minutes on its clock. Seen running, exited, gone or recorded, the note is dropped. A created container is still started on every tick until then, so a start that fails and then works passes. A core started again notes from its first tick: that only delays an end, by one bound per restart. A run that a kill left created after `AddRun` is started by the next core however long it was down (2026-11-24).
- An ended run's container, way out and network are removed as for any ended run, by its follower or else by the sweep. A removal that fails in the sweep is printed with the run's ID, and the sweep goes on to the next run; a failed list or store read still ends the tick (2026-11-24).
- The tick tests a card at the Git host after a round of fetching only when main or the card's published commit differs from this core's last test of it, which is kept in memory only. A core started again tests every card at once. Card 19's test of whether the change is in main is the same merge and is paced the same. A kill after the publication is cleared leaves a card that the next core publishes. A kill before leaves nothing written (2026-11-24).
- A run uses its card's repo. It starts from that repo's `main`, or from the card's branch in that repo's copy; its save goes there; and a review is told the diff made there. The run's row holds no repo, so a run carried on after a restart uses its card's repo as the core's list has it then. A card whose repo is not in the list starts no run, and its run in flight is not carried on; the tick says so on every tick and writes nothing (2026-11-25).
- Each repo's `main` is fetched from its own `origin`, at most once in 30 seconds, before a run of one of its cards starts. The tick starts the fetches of every such repo first, and waits for them at most 5 seconds in all. A repo's `main` is also fetched while one of its cards waits for the Git host, and Kiln's own, under a launcher, on every tick. Publishing, the check result command and the tests at the Git host work on each card's repo, after a round of that repo, and the comparison before the report reads every repo's `main` at its origin. A repo's failure to answer is printed with its name and holds no report. Only the update stays on Kiln's own repo (2026-11-25).
- The line that says the cards at the Git host are not tested, because a repo's main and its tree cannot be read, names the repo, as "repo <name>: ", when the instance has more than one repo, as the comparison's line does (2026-11-25).

## ADR 0036: A small launcher judges every update, and the store is copied before it

- The launcher is `kiln launch <the flags of kiln core>`, in `internal/launcher`. It starts `<its program> core <the same arguments>` and reads nothing in the data directory (2026-11-23).
- A core talks to the launcher on file descriptor 3, a socket of its own per start, named by `KILN_LAUNCHER=3`. The core makes the descriptor close-on-exec and unsets the variable at its start, so its children see neither (2026-11-23).
- A core reports `healthy` and may ask `replace <path>`. A replace is accepted only from a core that has reported, and only for an absolute path to a regular file of the launcher's user (2026-11-23).
- A new core is on probation for 2 minutes. One that ends or does not report in time is replaced by the previous program, started with `KILN_UPDATE_FAILED` and `KILN_UPDATE_FAILED_PROGRAM`. Until it reports, that program is started again only after a death by a signal, at most three times; a non-zero exit ends the launcher (2026-11-23).
- A core that crashes after its report is started again after 1 s, doubling to 60 s, and back to 1 s after 10 minutes of running. One that ends with 0, or a first start that ends before its report, ends the launcher (2026-11-23).
- Healthy is the core's report after one comparison that reads the store, the container engine, `main` at the Git host and its own screen. A Git host that does not answer is printed and does not count (2026-11-23).
- The programs and copies are in `<data>/programs/`: `kiln-<commit>`, and `kiln-<version>.db` or `kiln-by-hand.db`, each written as `.new` and renamed once whole. At each update the core removes, by exact name, every program and copy except its own program, its own copy and the new program. Nothing else in the directory is touched. One copy is kept (2026-11-23).
- Before the copy the core stops acting: moves are refused, the ticks, followers, publishers and fetches end as on Ctrl-C, and the screen stops. The copy is `VACUUM INTO` on the store's one connection, which closes the store in the same hold. The core then asks `replace` and exits 0. A failed copy or request ends the core with an error, and the launcher starts it again (2026-11-23).
- A core started with `KILN_UPDATE_FAILED` prints the reason, unsets both variables, and under the lock and before opening the store copies its copy to `store.db.restore`, removes `store.db-journal`, and renames the restore over `store.db`. The copy stays. It does not update to the commit of `KILN_UPDATE_FAILED_PROGRAM` again while automatic merging is off, which is kept in the store (ADR 0019 above) (2026-11-23).
- The new core, after its report and before it keeps the proxy, makes each image of its version's tag the plain name: `docker tag`, unless the plain name is that image already, and then the tag removed by exact reference. A core built by hand promotes nothing. So after a failed update the previous core finds the plain names as they were and keeps its proxy. A kill between tag and removal is finished by the next start, and a promotion that fails ends the core, which the launcher starts again (2026-11-23).
- At each update the core removes, by exact reference, every tag of 12 hex digits of the four images except its own version's and the new version's, as it removes their programs, under the core's context after the programs. A removal that fails is printed. No other image, tag or untagged image is touched (2026-11-23).

## ADR 0037: Kiln is built in a sealed container, and the core contains no C code

- The database is pure Go: SQLite translated to Go, through `ncruces/go-sqlite3` (ADR 0057).
- The README's build writes the program to `kiln.new` and renames it to `kiln` only after the build has succeeded and the file is executable. A failed build leaves no `kiln.new` and leaves a `kiln` from before as it was. The rename makes a new file, so a `kiln` that is running is not written over in place, which Linux refuses ("Text file busy") and which on macOS risks a code-signing crash (2026-11-20).
- The core's build is `seal.Build`. It uses the container `kiln-build-<instance>` with the label `kiln.build`, from `kiln-toolchain`, never pulled, with no network, no mount, no capabilities and the run's limits. The source is `git archive` on standard input, the program is for the core's own `GOOS` and `GOARCH`, with `-trimpath` and `-X main.version=<commit>`, and it comes out on standard output (2026-11-23).
- The update's program build uses `kiln-toolchain:<tag>`, the toolchain image it built from the new commit, instead of `kiln-toolchain` (2026-11-23).
- The images are built with `docker build` from `git archive` of the new commit on standard input, with the contexts of the README's lines: `go.mod`, `go.sum` and `images/toolchain/Dockerfile` for the toolchain, the whole commit for the proxy and the way out, and `images/run/` for the run image. Nothing is unpacked on the developer's machine. The proxy and the way out are built with no network, since they only compile from the toolchain image's module cache. The toolchain and run images are built with the network, for the base image, Go's modules and Claude Code. That is acceptable because both Dockerfiles are protected, what they fetch is pinned (the base by digest, the modules by `go.sum`, Claude Code by its SHA-256), and fetching a Go module runs none of its code. These builds run in the engine's builder and are not sealed as the program's build is (2026-11-23).
- The first install's one command is `scripts/kiln-up`. It builds the four images in the README's order, each only when the digest of its files differs from the one under `~/.cache/kiln` or the image is missing, the proxy and the way out with no network. It builds the program in `kiln-toolchain` with no network, `-trimpath` and the version, into `kiln.new`, renamed once whole (2026-11-24).

## ADR 0038: The container engine carries everything into and out of a run

> Since ADR 0059 a run with a list of hosts also reaches the hosts on its list. The lines below still hold.

- What is placed in a run, and how: the commit's files under `/work`, owned by the run's user, and the instruction at `/kiln/instruction.md`. The seal writes them as one archive into a container that has never started, and refuses absolute names, `..` and anything but files, directories and symlinks, so nothing else can be placed.
- The change is collected by saving the working tree in a throwaway container from the run image, with no network, the run's user and limits, and no mounts. The engine pipes the tree from the run's container into it, so nothing of it is unpacked on the developer's machine; what comes back is a tree and a pack of its new objects.
- A stage's documents and the run's sessions are kept as the archives the engine hands over, `documents.tar` and `session.tar` in the run's record, and are never unpacked on the developer's machine.
- A run's `result.json` holds `hosts`, its list of hosts, empty without one. The record of a run with a list holds `wayout.jsonl`, the way out's line per request: the target, the addresses, whether it was allowed or refused, the reason and the status. A run whose way out was gone when it was collected has none, and its `result.json` says `"wayout": "gone"` (ADR 0059) (card 12, 2026-11-19).
- A run's `result.json` keeps the result's `session_id` under `result` (2026-11-24).

## ADR 0039: A run image is a target repo's toolchain image with Kiln's layer on top

- Kiln's layer is `images/run/`. Claude Code is downloaded from the release bucket and checked against a SHA-256 per platform, and a run is user `kiln`, uid 1000, because Claude Code refuses `bypassPermissions` as root.
- A card that changes the pinned Claude Code takes the version that the release bucket's `stable` channel names on the day of its spec (`https://downloads.claude.ai/claude-code-releases/stable`), with the SHA-256s of that version's `manifest.json`, reads the changelog between the two versions, and runs both versions headless against the scripted upstream of `internal/run/testdata/claude` to compare the events and fields that `internal/run` reads. The pin was 2.1.326, which `stable` named that day (2026-11-25).

## ADR 0040: The core pushes the Claude credential to the proxy; the renewable secret never enters a container

- Whether runs that lose the credential while the core is down use up a card's retry, or pause the instance as rule 3 of ADR 0016 says for a failure of the instance, is listed in docs/open-points.md.
- The renewal runs beside the tick, so that a slow command never holds it up. The command runs with `sh -c` in the data directory, with no standard input, for at most 30 seconds, its process group ended with it, and what it prints, trimmed, is pushed, also when it is the same as before: at the core's start, five minutes after the last success (Claude Code's own interval for a key helper), and at once when the output of a run the core follows has an event `system/api_retry` with `error_status` 401, at most once in ten seconds (2026-11-23).
- The credential is unavailable when the command fails, runs out of time, prints nothing or more than 64 KiB, or when the push fails. The instance is then paused: its state in the store, with its history, the column `paused` of `instance` and the table `instance_entries` of store version 9 (ADR 0055), which the tick reads before it starts a run, so that nothing of the pause is kept only in memory (ADR 0035), and which the board shows in one line at the top, "Paused: the Claude credential is unavailable: " with the reason. The core says so on its terminal once per reason, with the command's standard error made printable and cut to its last 2 KiB, and never its standard output; runs in flight are left alone; it tries again every 30 seconds, and the first success ends the pause (2026-11-23).
- A run whose result carries `api_error_status` 401 says "the upstream refused the Claude credential (401)" in its reason, in place of its exit status and its result's subtype. Its card goes to "needs you" as before (2026-11-23).
- Since 2026-11-24, a run the upstream refused the credential to no longer puts its card under "needs you": it is run again by the rule once the pause ends, and does not use up its retry (ADR 0016). A credential that expires while the core is down is covered the same way: the run in flight ends refused, or it ends with no refusal and counts as failed (2026-11-24).
- The push goes through the container engine and has no port, which is stricter than "over a port that is open only on the developer's machine itself"; the developer changed that sentence of the decision on 2026-11-23, both halves: "through the container engine, into the proxy's container" in place of the port, and "whenever a run's output shows that the credential was refused" in place of "whenever the proxy reports that the credential was refused", since the proxy reports nothing and the core reads the refusal from a followed run's output (2026-11-23).
- The proxy's label `kiln.proxy` carries a version, 2 for a proxy that takes its credential by push, and the core keeps only a proxy of the version it starts, so that one started the old way, or with a weaker seal, is replaced; the version moves whenever what the seal sets on the proxy changes. A push has a limit of 30 seconds, and one that runs out of it makes the credential unavailable with a reason that is the same on every attempt. A pause that cannot be written to the store counts as a failure and is tried again in 30 seconds, and the core says a reason, or the end of a pause, only when the store's state changed, so once also across a restart (2026-11-23).
- A push that finds the proxy down (no container of its name, or one of Kiln's that is not running, `seal.ErrProxyDown`), as after a restart of the container engine, keeps the proxy as the core's start does (`KeepProxy`: started, or replaced) within 30 seconds. The same credential is then pushed again in the same renewal, without running the command again, and the core says on its terminal that the proxy is started again. A keep that fails or runs out of time pauses the instance with the reason "the proxy <name> is not running, and could not be started again: " and the error, or "..., and starting it again did not end within 30s". The next attempt, 30 seconds later, tries the push and the keep again. A push that fails for any other reason pauses as before and leaves the proxy alone. Unlike at the core's start, a proxy that cannot be kept here does not end the core (2026-11-25).
- Before the tick starts a run it looks at the proxy, one `docker ps` per run it is about to start. A proxy that is down holds the run back for that tick and asks for a renewal at once, at most once in ten seconds, which keeps the proxy as above; the run starts on a later tick. A look that fails for another reason holds nothing back. The look and the start are not one step, so a proxy that goes down in between still fails the run, by the rules for a failed run. The runs in flight are left alone (2026-11-25).

## ADR 0041: A sealed network has no gateway and holds one run

> Since ADR 0059 a run with a list of hosts shares its network with its way out as well. The lines below still hold; where one says that a run reaches the proxy and nothing else, it speaks of a run without a list.

- This decision's measurements were IPv4 only. On 2026-11-17 a run network with IPv6 off turned out to keep IPv6 on its bridge on the virtual machine, with a link-local address; a container with Docker's default capabilities has `NET_RAW`, sent raw frames to it, and reached the virtual machine's remote login and a published port. A run network is now closed in both families: IPv6 on, with the gateway mode isolated for IPv4 and IPv6, which leaves the bridge with IPv6 off and no address. The proxy has forwarding off in both families, and the seal's test checks both.
- As a non-root user a run has no effective capabilities whatever is dropped, and the bounding set matters only through setuid and file-capability programs. A run's container drops all capabilities and sets `no-new-privileges`, by the developer's decision of 2026-11-17.
- A run's network carries the label `kiln.run` with the run's ID, as its container does. The seal removes or attaches to a network of a run's name only with that label, and refuses one without it. A proxy whose container does not exist is not attached, so a run's network is removed without it, by the developer's decision of 2026-11-17.
- A run's network is created, and attached to, only for a proxy that carries the label `kiln.proxy`. One without it is refused before anything is created and left untouched, so that a mistyped proxy does not put another container on a run's network, by the developer's decision of 2026-11-17.
- A run's way out shares the run's network and is on the outward network `kiln-web` as well. It has forwarding off in both families, no capabilities, `no-new-privileges` and a read-only root. `kiln-web` is an ordinary bridge with no traffic between its containers (`enable_icc=false`) and the label `kiln.web`; one of the name without the label is refused, so that a way out is never put on a network Kiln did not make. It is never removed (ADR 0059) (card 12, 2026-11-19).

## ADR 0042: A card's current state and its history are written together

- A card carries two more facts beside its stage and what it waits for, so that no rule has to read the history (ADR 0054).
- The one place is `change` in `internal/store`: one transaction that checks, writes the card and writes its entry (ADR 0057).
- A card also carries when it got its state, `since`, written by `change` with the same time as the entry, so that the tick takes the card that has waited longest first without reading the history (rule 3). A store of version 5 takes the time of each card's last entry (card 17, 2026-11-20).
- The note on an approval is state, kept on the approved spec's row, and the core never reads it from the history (rule 3) (2026-11-23).
- A run's end and the rule's step that follows it are one change: `EndRunByRule` in `internal/store` writes the run's entry, at the state the run's end gives, and after it the rule's entry, of the cause rule and with no run, in the one transaction of `change`. The card's row has the rule's state (2026-11-23).
- A card's cost is a query over its runs, made when the board or the card is read, not a counter (rule 1) (2026-11-24).
- A card's interventions are a query over its entries, made when the board or the card is read, not a counter (rule 1). An entry counts when its cause is the developer, except the card's first entry (writing it), an entry from the backlog to spec waiting for a run (starting it), an entry from spec waiting for approval back to spec waiting for a run (a rejected spec, which belongs to the approval, rule 2), and the card's first entry from spec waiting for approval to implement waiting for a run (the planned approval). A move is told from the state of the card's previous entry. The entry of the instance that turns automatic merging on counts on no card (2026-11-24).
- In a card's history on the screen, a run's entry that the rule's entry follows in the same step, the one transaction of `EndRunByRule`, told by the two entries having the same time, is titled by its stage and what the run did: failed, passed, sent back or finished, never by the state it was written at. The card's JSON carries this as `did` on the entry, empty on every other entry (2026-11-24).
- An entry about a proposal changes no card. It carries the card's state as it is, writes neither the card's row nor `since`, and every reader of a card's last entry passes over it: the retry, the note a run is told, a failed publishing, a dropped predecessor and the board. A card written from a proposal is a card written, not an intervention, and a dismiss counts on no card (2026-11-24).

## ADR 0043: A card stores its stage and what it waits for; a run is in flight or has ended in one of four ways

- "The developer's approval" covers confirming a proposed drop, since a spec run ends with one of two results (ADR 0011).
- A card carries two more facts beside the two lists: its number of send-backs and whether its run was retried (ADR 0054).
- `change` in `internal/store` is the one place of rule 4, and the 11 valid pairings are one table in its code (ADR 0057).
- A run's ending is read off its record: finished when its container exited with 0, it was not killed for memory, it has a result with the subtype `success` and `is_error` false, the model is the one asked for, and the work is saved or nothing changed; failed otherwise, a missing result and a kill for memory included. A result with `is_error` reads `result is_error` in the reason. A failed run is run once more (ADR 0016). Until the stage cards a card waits in spec for a run, which is told the card's text; a finished run moves it to wait for the developer's approval (card 8, 2026-11-18; 2026-11-24).
- A finished spec run moves its card to wait for approval only with a spec it could read and a run that had the web. Otherwise the card goes under "needs you" with the reason, and the run stays finished (card 11).
- A card whose review passed waits in review for the developer's approval, a twelfth pairing, until the core publishes; ready to merge, review waiting for the Git host, comes with publishing. A finished implement run moves its card to review only with a commit saved; one that changed nothing stops under "needs you". A finished review run's card goes by the review's first line (card 14, 2026-11-19).
- Until dropped is a mark on the card, a dropped card is in done, waiting for nothing, and the reason of its last entry, the developer's, begins with "dropped by the developer", followed by the note; the board tells it apart by that entry. No column is added. `AddRun` refuses a run of a card that does not wait for one, and the tick's hold moves a card only from the state it read, so that a drop between the tick's read and the run's start wins (card 16, 2026-11-20).
- A card whose review passed waits for the Git host, review waiting for the Git host, once the developer publishes it, until it is merged, closed or sent back; a done card the Git host merged is told apart by its last entry, by the Git host with the reason `merged`, and the board shows it as merged (card 19, 2026-11-20).
- A card whose review passed waits in review for approval only without a publish command, or with a change to the workflow files, or without its branch. Otherwise it goes on by the rule to review, waiting for the Git host, in the transaction that ends the review run (2026-11-23).
- Backlog, waiting for room, also holds a card queued for its predecessors, and the reason names them. The developer's move from the backlog, waiting for the developer, is `start`, with no note: to spec, waiting for a run, or queued while a predecessor is not done. A card left in the backlog by a kill between its writing and its start has the same move. Whether a predecessor was dropped is read from its last entry, as the board reads it, until dropped is a mark on the card (2026-11-24).
- Backlog, waiting for room, also holds a card queued for its repo's limit (ADR 0014). The reason of its last entry begins with `waits for room in its repo `, and a developer's entry with that reason carries no note (2026-11-25).
- A recorded run whose `documents.tar` cannot be opened or read is failed, whatever its record says, with the reason naming the file, and its cost is kept. A damaged archive leaves the run finished, and the card needs you, as before (2026-11-24).

## ADR 0044: The UI sends requests; the core tells it about changes over one one-way event stream

- The stream also carries the entries of the instance, such as a pause (ADR 0055).
- Until the API comes, `kiln card --data <dir> <text>` stands in for it: it writes a card that waits in spec for a run. It takes the core's lock, so it never writes beside a running core (rule 5). The API card removes it in the pull request that adds the API (card 8, 2026-11-18).
- The core serves the API's first endpoints, and the screen, on a loopback address (`kiln core --listen`, `127.0.0.1:4747` by default), and refuses a request that does not come from its own page: a Host that is not the listen address gets 403, and a POST must be JSON, with an Origin, if it has one, of the page's own. Until the event stream comes, the page asks every 2 seconds. `kiln card` stays beside the screen for now, and the commands `kiln cards` and `kiln spec` of card 11's spec are not built (card 13, 2026-11-19).
- A core started with `--page` serves a page that is not built into its program. Rule 4 holds for the core as it runs by default. The flag is for work on the screen, and the file is trusted like the program: whatever it holds is "the core's own page" for rule 6, and may act through the API (2026-11-20).
- The board's JSON says the core's `build`, the first 16 hex digits of the SHA-256 of the embedded page, and the page carries the build it was served with in `data-build`. A page that sees another build on the board reloads itself, before it reads that answer further. It does not reload while a dialog is open, and it reloads once per build: a page reloaded for a build and still served another says so and stays. A core rebuilt with the same page reloads no page (2026-11-20).
- With `--page`, the build is the file's as it is at that moment: the page is served with it and the board says it, so a page left open reloads itself when the file changes. A file that cannot be read has no build, and a page left open stays as it is (2026-11-20).
- Until the core's report every POST gets 503, after the checks of rule 6. The board's JSON says `version` (2026-11-23).
- The board's tiles and the card's JSON carry `predecessors` and `queued_for`, the predecessors not yet done while the card is queued, both `[]` when empty. The card's JSON also carries `named_by`, with `id` and `title` (2026-11-24).
- `POST /api/proposals/{id}/decide` takes `{"action": "make-card"}` or `{"action": "dismiss", "note": …}`, with the checks of rule 6 and the 503 before the report. The board's JSON carries the open proposals as `proposals`, and a card's JSON carries `from_proposal`. A `make-card` repeated after a kill is refused, since the proposal is no longer open, so it never writes a second card (2026-11-24).
- The JSON of a board's tile and of a card carries `repo`, the name of the card's repo (2026-11-25).

## ADR 0045: Kiln's checks are one command that runs the tools directly in the toolchain image

- "The same everywhere" holds for what the check command can run inside the toolchain image. Tests that need the container engine run in the checks on the Git host only (ADR 0049); how they are started there is settled by the first card that has such a test.
- The toolchain image carries the Go modules of `go.mod` and `go.sum`, downloaded when it is built, so that the check finds them with the network off (ADR 0057).
- On the Git host's runner, `check/in-image` mounts Go's build cache, `KILN_GO_CACHE`, writable into the check's container and into the container that compiles the engine-test programs, still with the network off and the repo read-only. On the developer's machine the variable is ignored. `check/in-image --compile-only` compiles what the check compiles, runs none of it, and fills that cache (2026-11-20).
- The toolchain image carries the label `kiln.context`, the SHA-256 of its context's three files, and an image of that name with the same label is not built again (2026-11-20).
- The README builds the toolchain image from the same context as `check/in-image`: a tar of `go.mod`, `go.sum` and `images/toolchain/Dockerfile` on standard input, so that the image built by hand is the check's. A change to that list changes both (2026-11-20).
- A step of the check command runs `sh -n` on every file under `scripts/`, and fails on one that does not parse or is not executable (2026-11-24).
- `check/in-image --check-only` runs the check without the engine part, also on the Git host's runner. `check/in-image --engine-only <package>` runs only that package's engine tests, and on the developer's machine is a yes, as `--engine` is. A step of the check fails:
  - when the string literal `KILN_ENGINE_TESTS` appears anywhere but in the body of a `Test` function of `internal/seal`, `internal/run` or `internal/tick`;
  - when one of those has no engine test;
  - when the engine packages named in `check/in-image` or in the workflow's matrix differ from them (2026-11-25).

## ADR 0047: One repo with one Go module, divided by Kiln's parts, with guardrail files in a few named places

> Since ADR 0059 the way out is a part as well, and its program is a place of the seal. The lines below still hold.

- One more named place: Kiln's own stage instructions, in `instructions/` (ADR 0056).
- The places of the seal, which ADR 0048 names as protected, are `cmd/proxy/` and `internal/seal/`; the image of the proxy is under `images/`.
- Only `internal/seal` runs the `docker` command. A step of the check command fails when a Go file outside it that is not a test contains the string literal `"docker"`; it stops a slip, not an evasion.
- The core is `cmd/core`, built as `kiln`, and the steps of a run are `internal/run`, not `internal/core`: a package named after the whole core would take everything. Both call `internal/seal` and do not run the `docker` command.
- The step of the check command also fails on a string literal whose first word is `docker`, as in a shell line, or that is a path ending in `/docker`.
- `cmd/wayout/` is a place of the seal, and its image is under `images/` (ADR 0059) (card 12, 2026-11-19).
- One more named place: `scripts/`, the scripts that start and stop Kiln, which hand the core the upstream, the credential command and the developer's commands (2026-11-24).

## ADR 0048: Tests that need the container engine are run by hand, behind the developer's approval

- Creating a run's network and container, and starting the proxy from the credential command, are functions of `internal/seal`. The caller gives no network, mount, environment or limit. What a run can reach, read and obtain is asserted from inside a run's container in `internal/seal`'s test.

## ADR 0049: Kiln's repo is public on GitHub, under the developer's personal account

> Since ADR 0060 Kiln's app may change workflow files, and such a change is published only after the developer's yes. The lines below still hold.

- The engine tests are started by `check/in-image`: always on the Git host's runner, and on the developer's machine only with `--engine`, so that a test built from a card's branch does not run there unasked (ADR 0048). They are compiled in the toolchain image with the network off and run on the machine that runs the check, since the image has no engine.
- Besides the check on pull requests, a second workflow, `cache`, runs on every push to `main` and only fills the caches. It runs no check and no test (2026-11-20).
- The check on pull requests is several jobs side by side, each on its own runner:
  - `unit` (`--check-only`);
  - one `engine` job per engine package (`--engine-only`, `fail-fast: false`);
  - `check`, which waits for all of them with `if: always()` and passes only when every one succeeded.

  `check` stays the one required status check of `main`'s rule set (2026-11-25).
- The line above, "The engine tests are started by `check/in-image`: always on the Git host's runner…", holds except for a change that touches only docs (ADR 0031) (2026-11-25).

## ADR 0052: Until Kiln builds its own cards, its flow is run by hand

- Rule 4 holds with the core in the middle: the developer's own publish command holds the app's key, scans the title and the text, pushes and opens the pull request, and it lives outside the repo. `kiln core --publish-command <command>`, empty by default, is run with `sh -c` in the data directory, with no standard input, for at most five minutes with its process group, and with the core's environment plus `KILN_CARD`, `KILN_REPO`, `KILN_COMMIT`, `KILN_BRANCH`, `KILN_TITLE`, `KILN_TEXT_FILE` and, for a change to the workflow files the developer said yes to, `KILN_WORKFLOW_YES=1`, the same names taken out of what it inherits. Exit status 0 with a last line on standard output that starts with `https://` is published; anything else moves the card to review, needing you, with the exit status and the last 2 KiB of its standard error, made printable. The command may be run again for the same card and commit. No run and no test gets the key or a token (card 19, 2026-11-20).
- The commit the command publishes is the change put onto `main` as one commit, without a working tree: the merge of the card's branch into `main` as its tree, `main`'s head as its only parent, by Kiln, the pull request's title as its subject and `Kiln-Card: <id>` and `Kiln-Run: <id>` of the save at the branch's tip in its body. It is kept under `refs/kiln/publish/card-<id>`; the card's branch is not moved (card 19).
- Rule 4 with a core that publishes by itself: the developer's own command still holds the app's key and runs on the developer's machine. The core runs it once a review passes, and the developer's click is needed only for a change to the workflow files (2026-11-23).
- Rule 4 with the core in the middle holds for the check's result. `kiln core --check-result-command <command>`, empty by default, is run for every card at the Git host with a pull request: at once, and then at most every 2 minutes, never twice at once for one card. It runs with `sh -c` in the data directory, with no standard input, for at most one minute with its process group, and with the core's environment without any name that begins with `KILN_`, plus `KILN_COMMIT`, the published commit. Exit status 0 with the last line `pending`, `passed` or `failed` is a result. With `failed`, what it printed before is the check's output: valid UTF-8, made printable, the end of it kept, at most 16 KiB from a line start, marked when it was cut. `pending` and `passed` change nothing and are kept nowhere. Anything else is said on the core's error output when its text changes, and changes nothing. Standard error goes only to the core's output, at most 2 KiB and printable, never into the store, the screen or an instruction (2026-11-24).
- The check result command's contract, since it lives outside the repo: owner and repo are fixed in the command; `KILN_COMMIT` is 40 lowercase hex digits and is never evaluated, only quoted; no check yet for the commit is `pending`; standard output carries only the check's output and the result, never a token; the command holds what reading the check needs, at most a token that only reads the check of the one repo, not the app's key. On GitHub a fine-grained token cannot list a commit's check runs, so the command reads the runs of the check's workflow by `head_sha`, with a fine-grained token that has only "Actions: read" on the one repo (2026-11-24).
- Kiln is started from the repo: `scripts/kiln-up` builds, makes or updates the copy and runs `kiln launch`, and `scripts/kiln-down` stops the proxy. The publish command and the check result command stay outside the repo, holding what they hold, until the work repo's own publishing is designed. The script gives them to the core from `KILN_PUBLISH_COMMAND` and `KILN_CHECK_RESULT_COMMAND`, and without them the core gets neither flag (the developer's decision of 2026-11-24).
- Each repo's publish command is run for its own cards only, with `KILN_REPO` the copy of the card's repo, and each repo's check result command for its own cards' published commits only. A repo without a publish command publishes none of its cards: a review of one of them that passes waits for approval, and its moves have no `publish`, as a core without a command had. The core keeps no state across repos: a card's repo is written when the card is (2026-11-25).
- The publish command also gets `KILN_WORK_ITEM` when the card has a work item number (2026-11-25).

## ADR 0053: Each stage starts with a fresh session, and a stage that is sent back resumes its own

- A resumed run's result reports the cost of the whole conversation. Claude Code keeps the session's totals in its record and restores them on a resume or a fork, also in a new home that holds only the record, and across a change of model (tried with 2.1.326 on 2026-11-24). The cost counted for a run is what it added: its reported cost less the reported cost of the card's latest earlier run, of known cost, with the same `session_id`, which a plain `--resume` keeps. A run with no such earlier run counts its whole cost, and a difference below 0 is unknown. A fork gets a new `session_id`, so the card that resumes sessions resumes without `--fork-session` (2026-11-24).

## ADR 0054: A card carries its number of send-backs and whether its run was retried

- The number of send-backs is `send_backs` on the card's row (store version 10), 0 for every card that was there. One is added by every review that goes back and every return from the Git host because main moved, also when the rule stops the card because the number is two already. The developer's moves leave it, and approving a spec sets it to 0. Whether the run a card waits for is the retry is not a column. The store reads it from the card's last entry: an entry of the rule, with no run, with the card waiting for a run, whose reason begins with "the run failed, and the rule runs it once more; " or "the upstream refused the Claude credential on the retry; ". The first run's reason follows those words. Nothing writes an entry for a card whose run is in flight, so that entry stays last until the retry ends (2026-11-24).
- A failed check on the Git host adds one to the card's number of send-backs, as a review that goes back does, also when the card then waits for the developer (2026-11-24).
- A card whose published commit no longer merges counts one send-back when the publisher sends it to implement, not when the rule clears its publication. A branch that no longer collides, and is published again, counts none (2026-11-24).

## ADR 0055: The instance has state and history of its own, on the same stream

- An entry of the instance holds the instance's whole state after the change and its cause, as a card's entry does: `rule` for a pause and for automatic merging off, `developer` for turning it on. Entries from before store version 11 have cause `rule` (2026-11-23).
- A proposal's move is an entry of the card it was noticed on, marked by the proposal's ID. Making a card from it also writes the new card's first entry (2026-11-24).

## ADR 0056: Kiln's stage instructions live in one protected place

- The instructions are embedded in the core's program by the package `instructions`. A run's instruction is written once, when it starts, and a run in flight keeps it (card 11).
- `instructions/implement.md` and `instructions/review.md` are embedded beside `instructions/spec.md`. A run is told its stage's instruction and then, each under its heading, `## The card`, `## The approved spec`, `## The last review` and `## The change`, as its stage has them (card 14, 2026-11-19).
- A part of what a run is told that a run wrote (`## The last spec`, `## The last report`, `## The last review` and `## The approved spec`) is told inside a code fence with the info string `markdown`, as the change is told inside one with `diff`. The fence is backticks, one longer than the longest run of backticks in the part, so nothing in the part ends it and only the tick's own headings are headings. The card and the developer's note are not fenced, and the store keeps every document as the run wrote it (2026-11-20).
- The developer's note on the spec is told unfenced, like the card and the developer's note, between the approved spec and the parts after it (2026-11-23).
- A run in flight whose `instructions/<run>.md` is missing has it written again. If the text differs from the one its container or record was started with, or it cannot be written again, the run is ended as failed at once, with the reason naming the file (2026-11-24).
- The stage instructions were rewritten for agents, by the lens of the public writing-for-agents skill (github.com/mattpocock/skills, `skills/productivity/writing-for-agents`, read at commit 3216582): rules phrased by what to do, a sentence per stage that says when the run is done, each rule in one place, and negation kept for the hard guardrails, each paired with what to do. Every rule and fact they held stays, with the same force; the lines the core and the tests read stay byte for byte, and so does the heading "First, the card's size" (2026-11-25).

## ADR 0057: The store is SQLite, through ncruces/go-sqlite3, and the modules come in the toolchain image

- A card that changes the version of a Go module gets `go.mod` and `go.sum` from its spec run, which has the network: the spec gives both files whole, as `go mod tidy` wrote them, and the implement run writes them as given, since it cannot fetch a module. The check on the Git host builds the toolchain image from them, with the network, and is the first to compile against them (2026-11-25).

## ADR 0059: A run reaches the hosts on its stage's list, through a way out that holds no credential

- When a connection through the way out ends, the way out writes one more line to the run's `wayout.jsonl`. The fields are `time` (its end), `target` (as in the connection's first line), `sent` (bytes from the run to the host, with what the run sent behind its CONNECT), `received` (bytes from the host to the run, without the way out's `200` line), `duration_ms` (from the first line's time) and `end`: `run closed`, `host closed`, `error` with the text in `error`, or `stopped`. A line with `end` is a connection's end; the other lines are the requests' lines as before. The bytes are the totals of the copies; nothing inside a connection is read (rule 7) (2026-11-25).
- On SIGTERM the way out ends its open connections, writes their lines with `end` `stopped`, waits for them at most 2 seconds, and exits. Collecting a run stops its way out with `docker stop --timeout 5` before reading its output, so a connection still open at the run's end has its line. A way out that is killed (SIGKILL, `rm --force`, docker's kill after the timeout, a crash) writes no line for the connections open then. Their first lines stay without an end, and the card's page counts them as not counted. A way out from before this change writes no end lines at all (2026-11-25).
- The card's page shows, under each run's entry in the history, each host the run reached, with its number of connections and the bytes sent and received, read from `wayout.jsonl` on every request for the card. A host to which a run sent more than 64 KiB in all is marked. The value is a first one, chosen before any record counted bytes: one connection sent 1.0 to 2.2 KiB when it was measured, so 64 KiB is about 30 fresh connections to one host, or a few source files' worth (2026-11-25).

## ADR 0060: Kiln may change workflow files, and the developer says yes before such a change is published

- A change touches a workflow file when the diff of the card's branch from where it left `main`, renames counted at both names, has a file under `.github/workflows/`, or the entry `.github` or `.github/workflows`, or the branch has either as a symlink or a submodule. "The change" on the card's page marks it with the files, and "Publish" then asks first, with their names. The yes travels with the move, `{"action": "publish", "workflow_yes": true, "tip": …}`, with the tip of the change the page showed, and is kept with it; a yes for a tip that is no longer the branch's is refused with 409, and the page asks again; a `publish` without it for such a change is refused with 409, the sentence and the files. The publisher checks again: a change to the workflow files whose yes is not for the tip it publishes is not handed to the command, and the card needs you. The test of both is part of card 19 (2026-11-20).
- When the core publishes by itself, the yes is still asked on the screen. The rule never sends a change to the workflow files to the Git host: such a card waits in review for approval, with the reason and the files. The publisher's check of the yes for the tip it publishes stays (2026-11-23).
